## 分工边界

这是本项目的核心约定：**表现层归协作方，校验层与平台层归本仓库**。

| 层 | 由谁实现 | 负责什么 |
| --- | --- | --- |
| 表现层 | 协作方（`xiaocainu/`，默认 `http://127.0.0.1:8000`） | 对话交互、AI 意图理解与多轮追问、发票 OCR、把自然语言整理成结构化字段、把结果用自然语言回显 |
| 数据校验层与平台层 | 本仓库（`AiApprovalServer/`，默认 `http://127.0.0.1:8899`，路由前缀 `/api`） | 账号与权限权威（`App_Data/users.json`）、写入口唯一（报销单只能经 `/api/invoice/*` 写）、枚举与金额规则硬校验、服务端盖章字段、审批与执行、快照与版本回退、审计哈希链、网络安全（WAF、蜜罐、限流、请求签名防重放、越权记分与自动封禁） |

一句话约定：

> **AI 层可以随便理解，落地必须过校验层；校验层拒绝的，AI 层不许绕过。**

这条约定在协作方代码里有对应实现，不是君子协定：`xiaocainu/api/backend_client.py` 把失败分成两类——
`BackendRejected`（主服务器以 4xx 拒绝，属于"这单就不该写"）与 `BackendUnavailable`（连不上、超时）；
业务拒绝时**绝不回落直连飞书**，只有基础设施故障才按 `BACKEND_MODE` 决定是否回落。

边界上最容易搞错的几点：

| 事项 | 边界 |
| --- | --- |
| 报销单怎么写、写成什么值 | 协作方不许直连飞书主表，只能调 `/api/invoice/*`；申请人、工号、提交时间、合规结果、风险摘要、状态由服务端盖章，前端传了也不生效 |
| 谁能做什么 | 授权判定只在服务端（`Core/AccountPolicy.cs` + `Security/SecurityMiddleware.cs`），前端隐藏按钮只是 UX |
| 出错了怎么退 | 每次写飞书前存整行快照，管理员按版本日志回退（`POST /api/invoice/rollback`） |
| 事后怎么追 | 审计 JSONL 哈希链（`App_Data/audit.jsonl`），`GET /api/admin/audit/verify` 可整链校验 |
| 账号增删改 | 只能由管理员在本仓库管理后台或管理端接口操作；协作方那张飞书用户表是被写的镜像（当前登录链路的例外见下一节） |

## 项目组成

| 目录 | 角色 | 说明 |
| --- | --- | --- |
| `AiApprovalServer/` | **后端**（.NET 8 最小 API，零第三方 NuGet 依赖） | 鉴权、权限、报销单写入口、审批与执行、版本快照、审计哈希链、账号权威、飞书镜像 |
| `AiApprovalServer/wwwroot/` | 后端自带的页面（纯静态，原生 JS） | `index.html` 用户页、`finance.html` 财务台、`admin.html` 管理后台 |
| `xiaocainu/` | **协作方的对话式前端 + 网关**（Python / FastAPI） | 对话交互、AI 意图理解与多轮追问、OCR、结果回显；通过 `api/backend_client.py` 调本仓库接口 |
| `tests/` | 后端验收套件（Node，无需安装依赖） | 假模型、假飞书与各 e2e 套件，可完全离线运行 |
| `docs/` | 设计文档 | 本文所在目录 |

要点：**自带页面不是接入的必要条件**。协作方可以完全不用 `/finance`、`/admin`，只把本仓库当 API 后端使用；
反过来，本仓库不带协作方前端也能独立部署与验收（报销单列表为空、AI 对话降级为本地意图解析）。

## 三个入口

三个入口最终都打到本仓库后端（默认 `http://127.0.0.1:8899`，业务接口挂在 `/api` 前缀下）。

| 使用者 | 入口 | 由谁实现 | 主要动作 |
| --- | --- | --- | --- |
| 员工 | 协作方的对话式前端（AI 助手，默认 `http://127.0.0.1:8000/`） | 协作方表现层（`xiaocainu/`） | 用自然语言说"我要报销"，由 AI 多轮追问、OCR 取发票字段，整理成结构化字段后调本仓库提交，再用自然语言回显结果 |
| 财务 | 本仓库财务工作台 `/finance`（`wwwroot/finance.html`） | 本仓库自带页面 | 单据列表与筛选、审核、修改、删除；页面按权限显隐按钮，服务端仍会再校验一次 |
| 管理员与超级管理员 | 本仓库管理后台 `/admin`（`wwwroot/admin.html`） | 本仓库自带页面 | 账号与权限、审计日志与整链校验、版本回退、安全态势、飞书账号同步（另有待审批、出站通知、业务数据等面板） |

补充事实（均取自代码）：

| 项 | 事实 |
| --- | --- |
| 用户页 | 本仓库还自带一个业务工作台 `/`（`wwwroot/index.html`，启动横幅里叫"用户前端"），供员工直接对话、看任务与版本；员工走协作方前端时它可以不用 |
| 页面路由 | 固定映射：`/`、`/index.html`、`/finance`、`/admin`；`/finance/`、`/admin/` 及其子路径 302 重定向到无斜杠形态；不接受任何路径参数 |
| 按日志回退 | 回退动作（`POST /api/invoice/rollback`）由**管理后台**的「版本与回退」面板触发（`wwwroot/assets/admin.js`）；财务台只提示"到管理后台执行"，因为 `log.rollback` 权限只有管理员与超级管理员持有 |
| 角色限制 | `/api/admin/*` 要求角色为 `superadmin` 或 `admin`（`Roles.IsAdminSide`）；财务与员工访问会被 403 并给来源 IP 记 3 分 |
| 三个入口的共同点 | 都要先登录拿令牌，写请求都要带请求签名（见"鉴权与请求签名"） |

## 当前登录链路的真实状态

这一节如实描述现状，不作美化。**账号数据的权威在本仓库，登录判定也已经收到本仓库**：协作方前端的登录先问本仓库。

### 现状

| 环节 | 事实 |
| --- | --- |
| 本仓库侧 | 登录只读本机 `App_Data/users.json`（`UserService`），飞书用户表只是镜像、不参与鉴权 |
| 协作方侧 | 登录先调本仓库：协作方 `xiaocainu/api/auth_service.py` 的 `AuthService.login` → `_login_via_backend` → `xiaocainu/api/backend_client.py` 的 `login`，也就是 `POST /api/auth/login`，口令判定以本仓库为准；登录成功后协作方拿本仓库返回的账号资料（用户名、姓名、角色、工号）签发它自己的会话令牌，本仓库令牌按账号缓存在网关进程内供后续提交复用 |
| 本仓库明确拒绝 | 本仓库返回 4xx（口令错误、账号被禁用、账号被锁定、限流）时，协作方**直接返回 401/429，不再回落它自己的飞书用户表**（`backend_client.py` 把 4xx 归为 `BackendRejected`，语义就是"不许回落"） |
| 本仓库不可达 | 本仓库返回 5xx 或连不上（`BackendUnavailable`）时，看协作方 `.env` 的 `BACKEND_MODE`：`preferred`（默认）用协作方本地用户表兜底，`required` 直接以 503 拒绝登录 |
| 本仓库未启用 | `BACKEND_BASE_URL` 留空时 `mode` 为 `off`（`enabled()` 为假），保持原来的"只用本地用户表"的离线演示行为 |
| 角色映射 | 本仓库四个角色映射到网关三个标签：`employee` → 员工、`finance` → 财务、`admin` 与 `superadmin` → 管理员（`xiaocainu/api/auth_service.py` 的 `ROLE_LABELS`） |
| 结论 | **员工的登录判定以本仓库为准**；协作方那张飞书用户表只在"本仓库连不上且不是 `required` 模式"这一种情况下才会用到 |

上面这些分支都有单测兜底：`xiaocainu/tests/test_backend_authority.py` 共 7 项，覆盖主服务器接受、拒绝后不回落、不可达时 `preferred` 兜底、不可达时 `required` 拒绝、未启用时走本地表、角色标签映射，以及 `backend_client` 的 4xx / 5xx 分类。

### 剩下的已知边界

| 边界 | 说明 |
| --- | --- |
| 协作方表里存在、而本仓库不存在的账号 | `required` 模式下会被拒绝登录；`preferred` 模式下当本仓库不可达时仍能用协作方本地表登录（离线兜底）。这种登录没有本仓库会话，提交会回落**直连飞书**——等于绕过写入口、版本快照与审计 |
| 本仓库停用是否及时生效 | `required` 模式下本仓库停用账号或改口令，协作方前端下一次登录即以本仓库为准、立刻被拒；只有 `preferred` 模式且本仓库不可达时，才会退回协作方那张表的口径 |
| 审计与口径可能分叉 | 两张表各有一套启停与口令状态，排查"为什么他登不进来"时仍可能需要同时看两边 |

### 生产要做的部署选择

| 事项 | 做法 |
| --- | --- |
| 把 `BACKEND_MODE` 设为 `required` | 在协作方 `.env` 里设 `BACKEND_MODE=required`：本仓库返回 5xx 或不可达时**拒绝登录**（503）而不是回落本地表；`preferred` 是默认值，适合演示；`off`（或 `BACKEND_BASE_URL` 留空）表示完全不走本仓库 |

改造已经落地，剩下的只是这一项部署选择。设成 `required` 之后，"本仓库停用账号即员工无法登录"成立，也不再存在"用协作方本地表登录、提交绕过写入口"的离线通道。

### 存量账号怎么交过来

协作方表里已有的账号不必手工重建，用管理后台的「飞书账号同步」一次性导入：

| 步骤 | 接口或操作 | 说明 |
| --- | --- | --- |
| 先看对面有什么 | `GET /api/admin/users/feishu-rows` | 只读预览（`configured` / `count` / `rows`），不返回口令哈希 |
| 预演一次 | `POST /api/admin/users/sync-from-feishu`，`{"dryRun": true}` | 用当前账号库的只读快照跑同一套判断，不产生任何写入 |
| 正式执行 | `POST /api/admin/users/sync-from-feishu` | 只补本机没有的账号、认领已有账号的 `record_id`；**本机已有的账号一律不动**（口令、角色、启停都不覆盖） |

导入时的口令口径：对面存的是十六进制编码的 PBKDF2-HMAC-SHA256（迭代次数取 `Feishu:MirrorPbkdf2Iterations`，默认 `100000`），
导入后转成 base64 存进 `users.json`，因此**对方用原口令就能登录本仓库**；对面没有可用哈希的账号照样建，但 `needsPasswordReset = true`，管理员重置口令前登不进来。
另外，对面的「管理员」只会映射成 `admin`，永远不会变成超级管理员——**超管只能由配置播种或直接编辑 `users.json` 得到**。

在"口令判定以本仓库为准"的新链路下，这个导入动作更要紧：协作方表里存在、而本仓库不存在的账号在 `required` 模式下会被直接拒绝登录，
只有在 `preferred` 模式且本仓库不可达时才会退回协作方本地表（见上一节"剩下的已知边界"）。

## 部署形态

三种形态的差别只在"起什么、改哪些配置"，代码是同一份。

### 单机演示

| 项 | 内容 |
| --- | --- |
| 起什么 | 本仓库后端：`cd AiApprovalServer` 后 `dotnet run`（默认 `http://127.0.0.1:8899`）；协作方网关：`cd xiaocainu` 后 `python -m api.main 127.0.0.1 8000`（默认监听参数是 `0.0.0.0`，本地联调显式传 `127.0.0.1`） |
| 访问 | 浏览器分别访问两边的页面：本仓库 `http://127.0.0.1:8899/`、`/finance`、`/admin`；协作方 `http://127.0.0.1:8000/` |
| 要改的配置 | 本仓库：`config/secrets.local.json` 填飞书凭证（可选，不填则账号/权限/审批/审计仍可用，只有报销单接口不可用：列表查询返回 502 `FEISHU_UNAVAILABLE`，写入类操作返回各自的 `*_REJECTED`）；协作方：`.env` 里 `BACKEND_BASE_URL=http://127.0.0.1:8899` |
| 启动顺序 | **先起本仓库**：协作方前端登录时会先请它判定口令（`POST /api/auth/login`） |

### 前后端分离

本仓库只作为 API 后端提供给协作方前端使用，页面可以完全不部署给对方。

| 项 | 内容 |
| --- | --- |
| 起什么 | 只起本仓库后端（`dotnet run` 或发布产物），协作方前端独立部署 |
| 写请求必须签名 | 带 `Authorization: Bearer` 且方法为 `POST`/`PUT`/`PATCH`/`DELETE` 的请求必须带 `X-Timestamp`、`X-Nonce`、`X-Signature`（HMAC-SHA256）；算法、拼串与示例见 [API参考.md](API参考.md) 第 2.3 节 |
| 跨站写请求要放行来源 | 浏览器发起的写请求会带 `Origin`。认证不用 Cookie，但服务端对 `POST/PUT/PATCH/DELETE` 另有来源校验：命中 `Security:TrustedOrigins` 白名单，或与本服务看到的 `{Scheme}://{Host}` 严格同源才放行，否则 403 `BAD_ORIGIN`。协作方前端与后端**不同源**（例如前端在 `http://127.0.0.1:8000`、后端在 `http://127.0.0.1:8899`）时，必须把前端的来源加进白名单，否则写请求会被拦掉 |
| 白名单怎么配 | `appsettings.json` 的 `Security:TrustedOrigins`（数组），或环境变量 `AISERVER_TRUSTED_ORIGINS`（多个值用分号、逗号或空格分隔）；必须是带协议的完整来源，不支持通配符 |
| 不受影响的情况 | 不带 `Origin` 的客户端（`curl`、脚本、服务端调用，例如 `xiaocainu/api/backend_client.py` 用的 `urllib`）本来就不受这条校验约束，由请求签名负责真实性 |

### 生产

| 项 | 内容 |
| --- | --- |
| 对外形态 | 反向代理终止 TLS，本仓库**只监听回环**（默认 `http://127.0.0.1:8899`），代理通过回环转发；不要改成 `0.0.0.0` 绕过代理 |
| 四个后端密钥 | `AISERVER_JWT_SECRET`（登录令牌与审批链接令牌签名）、`AISERVER_AES_KEY`（32 字节 base64）、`AISERVER_PEPPER`、`AISERVER_AI_KEY`——走环境变量，或写进 `config/secrets.local.json` |
| 飞书凭证 | 同样走环境变量（`AISERVER_FEISHU_APPID` / `AISERVER_FEISHU_APPSECRET` / `AISERVER_FEISHU_APPTOKEN` / `AISERVER_FEISHU_TABLEID` / `AISERVER_FEISHU_USERTABLEID`，命名规则为 `AISERVER_FEISHU_<配置键名大写>`）或 `config/secrets.local.json` |
| `config/secrets.local.json` 的性质 | 已被 `.gitignore` 忽略，且被 `AiApprovalServer.csproj` 显式设为 `CopyToOutputDirectory=Never` / `CopyToPublishDirectory=Never`，**不会被复制进构建产物与发布包**（只放行 `config/secrets.local.example.json` 模板）；它同时装着飞书凭证与 `BootstrapAdmin` 初始超管配置，交付前应清空 |
| 来源校验 | 反代场景必须显式设置 `Security:TrustedOrigins`（首选），或让代理把 `Origin` 改写成"本服务看到的 scheme + 同一个 Host"（备选）；HSTS 需在代理侧配置 |
| 客户端 IP | 服务端只信任 TCP 对端地址、不解析 `X-Forwarded-For`，因此按 IP 的限流在代理后近似全局限流，需要相应放大阈值；代理侧建议把 `X-Forwarded-For` 覆盖为直连地址 |
| 完整清单 | 见 [部署与配置.md](部署与配置.md) 第十节（身份与密钥 / 访问面 / AI 与通知 / 数据与运维） |

### 协作方没有 .NET 环境时怎么本地联调

这一层的前端同学通常只装 Python，装不上 .NET SDK。**不需要为了跑起来去装 SDK**，按代价从低到高有三种办法：

| 办法 | 适用 | 怎么做 |
| --- | --- | --- |
| 免安装运行包（推荐） | 只想**调用**本仓库、不想编译 | 我们发布的自包含包（`dotnet publish AiApprovalServer/AiApprovalServer.csproj -c Release -r win-x64 --self-contained true -o <目录>` 生成，约 100 MB，解压 43 MB 左右），解压后双击 `AiApprovalServer.exe` 即可，目标机不需要任何 .NET 组件。包内附 `怎么运行-读我.md`，账号、飞书配置、端口、启动顺序都写在里面 |
| 装 .NET 8 运行时 | 手上有我们编译好的 `dll` | 装 **ASP.NET Core Runtime 8**（不是 SDK，体积小得多），然后 `dotnet AiApprovalServer.dll` |
| 装 .NET 8 SDK | 需要改本仓库代码 | 装 SDK 后 `cd AiApprovalServer && dotnet run`；这也是仓库 README 的默认路径 |

注意两点：

- **运行包是编译产物**，不要提交进仓库（约 100 MB），每次由我们重新生成并在 Release 里附带；协作方改本仓库代码不会生效，要动后端就提 PR。
- 账号、审批、审计、财务台这些**不依赖飞书**也能跑：不填飞书凭证时只有报销单接口返回 502 `FEISHU_UNAVAILABLE`，其余能力照常。要联调真实写单再填 `config/secrets.local.json`。

## 鉴权与请求签名

协作方接入必须过这一关，细节见 [API参考.md](API参考.md) 第 2 节。这里只列接入方最常用的部分。

| 项 | 内容 |
| --- | --- |
| 登录 | `POST /api/auth/login`，请求体 `{ "userName": "...", "password": "..." }`；成功响应 `data` 里给出 `token`、`signKey`、`expiresAt`、`user`、`signing` |
| 令牌使用 | 后续请求带 `Authorization: Bearer <token>`；默认有效期 `Security:TokenMinutes`（120 分钟） |
| 签名密钥 | `data.signKey`（同一值也编码在 JWT 载荷 `sk` 里），每次登录重新随机生成 |
| 需要签名的请求 | 带令牌且方法为 `POST` / `PUT` / `PATCH` / `DELETE` 的请求；所有 `GET` 不需要 |
| 三个头 | `X-Timestamp`（Unix 毫秒）、`X-Nonce`（16~128 字符、同一用户同一 nonce 在窗口内只能用一次）、`X-Signature` |
| 拼串 | 五段用单个换行符连接、无尾随换行：`METHOD` / `PATH?QUERY` / `X-Timestamp` / `X-Nonce` / `SHA256_HEX(rawBody)` |
| 签名值 | `Base64(HMAC-SHA256(key=UTF8(signKey), message=UTF8(canonical)))`，标准 Base64（不是 base64url） |
| 失败表现 | 签名/时间戳/nonce 任一不合格 → 401 `BAD_SIGNATURE`，并给来源 IP 记 2 分 |

对接方如果不想自己实现签名，可以照抄 `xiaocainu/api/backend_client.py` 的 `_sign`：它只用标准库（`hmac` / `hashlib` / `base64`），
拼串顺序与服务端 `Security/SecurityMiddleware.cs` 的 `VerifySignature` 一致。

## 协作方接入的最短路径

### 装依赖

| 侧 | 命令或要求 |
| --- | --- |
| 本仓库 | .NET 8 SDK（构建）/ .NET 8 运行时（仅运行）；无第三方 NuGet 包；Node.js 只在跑验收套件时需要 |
| 协作方 | Python 3（FastAPI 网关）；`requirements.txt` 含中文注释，在 GBK 默认编码的 Windows 上 `pip install -r` 会解码失败，先设 `$env:PYTHONUTF8 = '1'`，或直接 `python -m pip install fastapi uvicorn` |

### 配 `.env`

| 键 | 取值与作用 |
| --- | --- |
| `BACKEND_BASE_URL` | 本仓库地址，例如 `http://127.0.0.1:8899`；留空 = 不启用（等价于 `off`，保持直连飞书的老行为） |
| `BACKEND_MODE` | `preferred`（默认）：优先本仓库，仅在连不上/会话过期时回落直连飞书；`required`：必须走本仓库，连不上或业务拒绝都直接报错；`off`：完全不走本仓库 |
| `BACKEND_TIMEOUT` | 单次 HTTP 超时（秒），默认 `15` |
| 其它 | 协作方自己那套配置（飞书凭证、用户表 id、`AUTH_SECRET` 等）照旧，见 `xiaocainu/.env.example` |

登录也受 `BACKEND_MODE` 约束：本仓库返回 4xx（口令错误、账号被禁用、账号被锁定、限流）时协作方直接 401/429，不回落它自己的飞书用户表；
只有本仓库返回 5xx 或连不上时，才由这个键决定——`preferred` 用协作方本地用户表兜底，`required` 直接拒绝登录（503）。
这四种情形都有单测覆盖：`xiaocainu/tests/test_backend_authority.py`，共 7 项，覆盖主服务器接受 / 拒绝 / 不可达 / 未启用四种情形以及角色标签映射与状态码分类。

可审计部署建议直接上 `BACKEND_MODE=required`：`preferred` 下"会话过期"这类基础设施故障仍会回落直连飞书写一次，
同一笔单可能因此出现两行（一行有审计与快照、一行没有）。

## 字段与枚举口径

**不需要前端传**（传了也会被服务端用登录身份与预审结果覆盖）：`申请人`、`工号`、`记录提交时间`、`合规结果`、`风险摘要`、`状态`。
`单号`由飞书自动编号生成，写完由服务端回取（有极短的最终一致性延迟，取不到时返回空串，不会编造"系统生成中"）。

**需要前端传**（枚举一律以 `GET /api/invoice/meta` 为准，不要手抄）：

| 字段 | 约束 |
| --- | --- |
| `department` | 必须命中部门枚举（11 项，取自 `meta`） |
| `rtype` | `差旅费` / `招待费` / `办公用品` / `交通费` |
| `amount` | 0.01 到 100000 |
| `reason` | 2 到 200 个字符（必填，服务端会拒绝空事由） |
| `hasInvoice` | `有票` / `无票` / `未提`；`无票` 会被硬性阻断 |
| `city` | 差旅费必填，必须命中城市清单（37 项） |
| `invoiceDate` | `yyyy-MM-dd`，非法返回 400 `BAD_DATE`；`backend_client.py` 会把 `2026/10/3`、`2026年10月3日` 之类归一后再发 |
| `invoiceInfo` | 发票信息（号码；销售方），不超过 128 个字符 |
| `taskId` | 可选，关联任务号（审计用） |

`GET /api/invoice/meta` 还给出城市分级上限（`cityTierCaps`）、只读列（`readonlyFields`）、服务端盖章列（`serverStampedFields`）、
财务可改列白名单与当前登录角色的能力位（`canSeeAll` / `canReview` / `canUpdate` / `canDelete` / `canRollback`），前端据此显隐按钮即可。

失败语义必须分清（这是"唯一写入口"能否成立的关键）：

| 失败类型 | 例子 | 协作方应如何处理 |
| --- | --- | --- |
| 业务拒绝（4xx，`code` 形如 `SUBMIT_REJECTED` / `REVIEW_REJECTED` / `UPDATE_REJECTED` / `DELETE_REJECTED` / `ROLLBACK_REJECTED` / `BAD_DATE` / `FORBIDDEN`） | 无票阻断、部门不在枚举内、金额越界、事由缺失 | **绝不回落直连飞书**，把服务端 `message` 原样回给用户，让用户改数据后重来 |
| 基础设施故障（连不上、超时、`502 FEISHU_UNAVAILABLE`） | 本仓库没起、超时、会话过期；`502 FEISHU_UNAVAILABLE` 只出现在列表查询 | `preferred` 可回落直连飞书（只影响这一笔）；`required` 直接报错 |
| 飞书不可用导致的写失败 | 提交时飞书未配置或调用失败，服务端返回 400 `SUBMIT_REJECTED`（审核/修改/删除同理走各自的 `*_REJECTED`） | 这类失败在协作方侧按**业务拒绝**处理（`backend_client.py` 只按 HTTP 4xx 分类），因此同样**不会**回落直连飞书——不让写入绕过写入口，是有意为之 |

## 排障速查

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 登录响应里 `backend` 是"本地用户表校验（主服务器未启用或不可达）"，或提交时提示"主服务器暂时不可用" | 本仓库没起 / 地址不对，且当前不是 `required` 模式（`required` 下不会兜底，直接 503 拒绝登录）；也可能是该账号在本仓库不存在 | 起本仓库并确认该用户名与口令在本仓库也存在（权威在本机 `users.json`）；要接管已有账号用管理后台的「飞书账号同步」补进来；生产建议把协作方 `BACKEND_MODE` 设为 `required` |
| 提交后答复"这张单没有提交成功：…部门必须…" | 业务规则拒绝（不回落） | 按提示改数据后重新提交 |
| 提交后答复"主服务器暂时不可用" | `required` 模式且本仓库不可达 | 起本仓库，或临时切 `preferred` |
| `preferred` 模式下同一笔单出现两行 | 曾回落直连飞书写过一次，之后又走本仓库写了一次 | 只看本仓库写入的那一行（有审计与版本）；生产建议用 `required` 模式杜绝 |
| 浏览器写请求返回 403 `BAD_ORIGIN` | 协作方前端与本仓库不同源，来源未进白名单；或反代终止 TLS 导致来源不一致 | 把前端实际来源加进 `Security:TrustedOrigins`（`AISERVER_TRUSTED_ORIGINS`），或让代理把 `Origin` 改写为"本服务看到的 scheme + 同一个 Host" |
| 写请求返回 401 `BAD_SIGNATURE` | 缺签名头、时间戳超窗、nonce 复用、或对"实际发出的字节"之外的 body 做了哈希 | 按 [API参考.md](API参考.md) 第 2.3.4 节的示例逐段核对；代理机与服务机要有 NTP 时间同步 |
| 登录返回 429 或提示锁定 | 命中 `Limits:LoginPerFiveMinutesPerIp`，或连续失败触发账号锁定（默认 5 次 / 15 分钟，锁定状态持久化在 `users.json`） | 等待或由管理员解封；批量验收时放宽阈值 |
| 报销单列表查询返回 502 `FEISHU_UNAVAILABLE` | 未配置飞书（或调用失败） | 按 [飞书镜像对接.md](飞书镜像对接.md) 第 10 节配置凭证与表 id；账号、权限、审批、审计不受影响 |
| 账号同步返回 409 `SYNC_UNAVAILABLE` | 飞书四项凭证缺一，或从对面用户表读到 0 行 | 先用 `GET /api/admin/users/feishu-rows` 看 `configured` 与 `rows`，再核对 `Feishu:UserTableId` |
| 页面 404 | 内容根没找到 `wwwroot` | 在 `AiApprovalServer/` 目录下 `dotnet run`，或运行含 `wwwroot` 的发布目录；启动横幅里的"数据目录"能反推内容根 |

## 一句话总结

本仓库是**后端与平台层**（账号权威、唯一写入口、审批与回退、审计哈希链、安全防线），
协作方是**表现层**（对话、意图理解、OCR、回显）；
三个入口（协作方对话前端、财务台 `/finance`、管理后台 `/admin`）都打到同一个后端 `http://127.0.0.1:8899` 的 `/api`；
写请求要签名、跨站要放行来源、生产要反代终止 TLS 且只让后端监听回环；
而"登录判定以本仓库为准"这件事已经落地：协作方先问本仓库、4xx 不再回落它那张飞书用户表，
剩下的只是把协作方 `BACKEND_MODE` 设为 `required`，消掉"本仓库不可达时用本地表登录"这条离线兜底路径。
