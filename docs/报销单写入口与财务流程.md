# 报销单写入口与财务流程

本文说明**报销单为什么只能由本服务写、写的时候到底做了什么、财务与管理侧能做什么、出错怎么办**。
面向两类读者：要接我们这个后端的协作方前端，以及维护这套服务的开发者。

对应代码：
`Core/InvoicePolicy.cs`（判定规则）、`Services/InvoiceService.cs`（写入口实现）、`Services/FeishuApi.cs`（飞书客户端）、
`Api/InvoiceApi.cs`（对外接口）、`Core/AccountPolicy.cs`（权限矩阵）、`wwwroot/finance.html` 与 `wwwroot/assets/finance.js`（财务工作台）、
`tests/e2e-invoice.mjs`（行为契约，本文每条规则都能在该套件里找到对应断言）。

相关文档：[API参考.md](API参考.md)（接口字段与错误码）、[账号与权限设计.md](账号与权限设计.md)（四角色与权限键）、
[飞书镜像对接.md](飞书镜像对接.md)（账号镜像与凭证配置）、[业务场景与操作手册.md](业务场景与操作手册.md)（端到端操作走查）。

## 一、为什么写入口必须唯一

报销单的真实数据在飞书多维表里，但**只有我们的服务端可以写它**：协作方前端调我们的接口，我们再去写飞书。理由有三条，缺一条都会出问题。

| 理由 | 不集中写会怎样 | 我们怎么做 |
| --- | --- | --- |
| 审计与追责 | 谁都能拿 app_secret 直连飞书改表，改完没有任何记录，出事查不到人 | 每次写操作先落版本快照、再写审计哈希链（`audit.jsonl`），动作与新旧值都能追溯 |
| 可回退 | 直连写入没有"旧值"，删错了就是永久丢失 | 写前存整行快照（版本库 `versions.json` + blob），管理员可按日志一键回退 |
| 枚举与越权防护 | 前端可以自由拼单选项（飞书单选项写入会自动新建选项），也能替别人填单、查别人的单 | 服务端白名单校验枚举、金额、城市分级；申请人/工号/状态由服务端盖章；列表与详情都做归属校验 |

一并被挡住的还有：绕过审批直接改状态、把已通过的单子改回待审核、用非法枚举污染飞书表的选项集合。

## 二、一次提交的完整链路

以员工在小财前端说"提交一笔市场部招待费 2500，有票，上海，2026-10-01"为例：

| 步骤 | 做什么 | 代码位置 |
| --- | --- | --- |
| 一 | 前端带 JWT 与请求签名调用 `POST /api/invoice/submit` | `Api/InvoiceApi.cs`（`/submit`） |
| 二 | 安全中间件校验令牌、令牌世代、请求签名与来源；通过后注入登录身份 | `Security/SecurityMiddleware.cs` |
| 三 | 权限校验：必须有 `invoice.submit`（四种角色都有） | `Core/AccountPolicy.cs` |
| 四 | 限流：每账号 5 分钟 30 次提交 | `Api/InvoiceApi.cs` |
| 五 | 日期解析（`yyyy-MM-dd`）与参数清洗（`Api.Clean`） | `Api/InvoiceApi.cs` |
| 六 | 构造草稿并做确定性校验：枚举、金额区间、事由长度、差旅必须有合法城市、发票信息长度 | `InvoicePolicy.ValidateSubmit` |
| 七 | 合规预审：无票阻断；其余超标项记为风险并生成一句话摘要 | `InvoicePolicy.Evaluate` |
| 八 | 服务端盖章：申请人 = 登录姓名、工号 = 登录工号、状态 = 待审核、提交时间 = 东八区当前毫秒 | `InvoiceService.SubmitAsync` |
| 九 | 字段适配：剔除表里不存在的列、永远不写只读列 | `InvoiceService.FitAsync` |
| 十 | 写飞书主表并取回 `record_id` | `FeishuApi.CreateRecordAsync` |
| 十一 | 记版本：`kind=invoice`、`operation=submit`、撤销日志 `action=submit`（回退即删除该行） | `VersionStore.RecordAsync` |
| 十二 | 记审计：`invoice.submit`，`SUCCESS` 时写明类型、金额、合规结果与版本号 | `AuditLog.WriteAsync` |
| 十三 | 返回 `recordId` 与提示；失败一律不写飞书（校验阶段失败）或写明飞书错误（写入阶段失败） | `Api/InvoiceApi.cs` |

要点：**校验与合规预审都在写飞书之前**，所以非法请求不会在飞书里留下垃圾行；写入阶段失败时会返回飞书原始 `code/msg`，不会假装成功。

## 三、服务端盖章字段与只读字段

前端即便传了这些字段也不生效，写入值一律由服务端决定。

| 分类 | 字段 | 说明 |
| --- | --- | --- |
| 服务端盖章 | `申请人` | 登录账号的姓名。员工无法替他人填单 |
| 服务端盖章 | `工号` | 登录账号的工号（`E` + 四位，服务端分配） |
| 服务端盖章 | `记录提交时间` | 东八区当前时间毫秒时间戳 |
| 服务端盖章 | `合规结果` | 由合规预审产出，只有 `通过` 与 `风险` 两种取值 |
| 服务端盖章 | `风险摘要` | 由合规预审产出；无风险时为 `无` |
| 服务端盖章 | `状态` | 提交时固定 `待审核` |
| 只读列 | `单号` | 飞书自动编号（`BX-` + 六位），代码永不写；前端传了会被拒（见"修改"一节） |
| 只读列 | `发票附件` | 附件列，由上传流程写入，服务端不通过文本接口写 |

财务侧可修改的列（白名单）：`部门`、`报销类型`、`金额`、`事由`、`票据状态`、`城市`、`发票日期`、`合规结果`、`风险摘要`。
审核动作另外会写：`状态`、`审核人`、`审批意见`、`审批时间`。

接口 `GET /api/invoice/meta` 会把上述三组字段原样下发，前端应据此渲染而不是自己写死。

## 四、枚举字典（与飞书表单选项逐字一致）

改枚举必须两边同步：飞书表里对应单选字段的选项 + `Core/InvoicePolicy.cs` 的字典。只改一边会出现"服务端放行但飞书写失败"或"飞书有选项但服务端拒绝"。

| 字典 | 取值 | 数量 |
| --- | --- | --- |
| 部门 | `研发部`、`市场部`、`财务部`、`人力资源部`、`行政部`、`生产部`、`销售部`、`采购部`、`信息技术部`、`质量管理部`、`客户服务部` | 11 |
| 报销类型 | `差旅费`、`招待费`、`办公用品`、`交通费` | 4 |
| 票据状态 | `有票`、`无票`、`未提` | 3 |
| 合规结果 | `通过`、`风险` | 2 |
| 状态 | `待审核`、`审核中`、`已通过`、`已驳回` | 4 |
| 城市 | 一线：`北京`、`上海`、`广州`、`深圳`；新一线：`成都`、`杭州`、`武汉`、`西安`、`南京`、`重庆`、`苏州`、`天津`、`长沙`、`郑州`、`青岛`、`宁波`、`东莞`、`无锡`、`沈阳`、`昆明`、`佛山`、`合肥`、`济南`；二线：`福州`、`厦门`、`哈尔滨`、`太原`、`南昌`、`南宁`、`贵阳`、`石家庄`、`兰州`、`大连`、`常州`、`温州`、`烟台`、`泉州` | 37 |

城市分级住宿上限：一线 **500** 元/晚、新一线 **350** 元/晚、二线 **250** 元/晚（由 `InvoicePolicy.CityTierCap` 给出，`GET /api/invoice/meta` 的 `cityTierCaps` 会下发三个数字）。

注意两点差异，避免对接时踩坑：

- 飞书表「合规结果」列的下拉里可能还有历史选项（例如 `驳回`、`超2000需总经理审批`），**服务端只写 `通过` 与 `风险`**；`驳回` 这类终态语义改由「状态」列表达。
- 服务端不做"城市白名单强校验"以外的推断：`城市` 为空只在非差旅类被允许；差旅费必须给城市且必须命中上面 37 个之一。

## 五、合规预审规则

预审是确定性代码（不调用模型），结论分三种：**阻断**（不允许提交）、**风险**（允许提交但写摘要）、**通过**。

| 规则 | 判定 | 结果 |
| --- | --- | --- |
| 无票 | `票据状态 = 无票` | **阻断**：返回"票据状态为「无票」：缺少合规发票，提交前无法放行，请补齐发票后再提交" |
| 票据未提 | `票据状态 = 未提` | 风险：`票据状态未提，提交前需确认合规发票` |
| 招待费超标 | `报销类型 = 招待费` 且 `金额 > 2000` | 风险：`单次招待费超2000元，需总经理事前审批` |
| 办公用品超标 | `报销类型 = 办公用品` 且 `金额 > 5000` | 风险：`超5000元，走采购流程，不适用个人报销` |
| 差旅住宿分级 | `报销类型 = 差旅费`，城市命中分级且 `金额 > 该城市上限` | 风险：`<城市>属住宿分级上限<上限>元/晚，超标需事前审批` |
| 差旅金额偏大 | `报销类型 = 差旅费` 且城市不在分级清单内且 `金额 > 3000` | 风险：`差旅费金额较大，请确认住宿城市与晚数是否符合分级标准` |
| 开票超期 | 有发票日期且 `今天 - 发票日期 > 30 天` | 风险：`距开票超30天，需附情况说明` |

提交校验（在预审之前执行，任一不通过直接 400）：

| 校验项 | 规则 |
| --- | --- |
| 部门 | 必须命中 11 个部门之一 |
| 报销类型 | 必须命中 4 类之一 |
| 票据状态 | 必须命中 3 个值之一 |
| 金额 | 必须在 **0.01 到 100000** 之间 |
| 事由 | 去空白后 **2 到 200** 个字符 |
| 城市 | 差旅费必填且必须命中 37 城；非差旅可空，填了也必须命中 |
| 发票信息 | 不超过 **128** 个字符 |

风险摘要的拼接方式是分号连接（`；`），所以 `招待费 2500 元` 的摘要是"单次招待费超2000元，需总经理事前审批"。

## 六、状态流转

| 当前状态 | 目标 `审核中` | 目标 `已通过` | 目标 `已驳回` | 目标 `待审核` |
| --- | --- | --- | --- | --- |
| `待审核` | 允许 | 允许 | 允许 | 拒绝 |
| `审核中` | 允许 | 允许 | 允许 | 拒绝 |
| `已通过` | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| `已驳回` | 拒绝 | 拒绝 | 拒绝 | 拒绝 |

拒绝文案（`InvoicePolicy.ValidateReviewTransition`）：

- 改回待审核：`审核动作不能把状态改回「待审核」`
- 终态再改：`该单据已通过，不能再改状态（如需更正请走管理员回退）` 或 `该单据已驳回，不能再改状态（如需更正请走管理员回退）`
- 目标状态非法：`目标状态必须是以下之一：待审核、审核中、已通过、已驳回`

另外两条硬约束：

- 审批意见必须 **2 到 300** 个字符，否则拒绝。
- 审核人由服务端写成**当前登录人姓名**，前端传什么都会被忽略。

## 七、数据边界

| 角色 | 列表范围 | 详情 | 提交 | 审核 | 修改 | 删除 | 回退 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 员工 `employee` | 仅本人（按登录姓名过滤） | 仅本人 | 允许 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| 财务部 `finance` | 全部（`scope=all`） | 全部 | 允许 | 允许 | 允许 | 拒绝 | 拒绝 |
| 管理员 `admin` | 全部 | 全部 | 允许 | 允许 | 允许 | 允许 | 允许 |
| 超级管理员 `superadmin` | 全部 | 全部 | 允许 | 允许 | 允许 | 允许 | 允许 |

实现细节：

- 列表：先拉飞书记录，再按角色过滤（`InvoicePolicy.CanSeeAll` / `BelongsTo`）；员工看到的 `scope` 是 `mine`。
- 详情：拿到记录后再做一次归属校验，员工读别人的单返回 403 `FORBIDDEN`（文案"无权查看他人的报销单"）。
- 归属判定优先用**工号**（`BelongsTo` 先比登录人工号与记录里的「工号」列，唯一且不随改名漂移）；只有历史数据缺工号时才回退到姓名匹配，因此重名不会串单。
- 拒绝类调用（越权审核/删除/回退）会返回 403，并且**会累加 IP 攻击分**：越权类操作每次计 2 分，默认 8 分封禁。写前端时不要"先试着调一下看看"，要么按权限隐藏按钮，要么接受被封的风险。

## 八、回退语义与限制

回退的入参是**版本号**（`versionId`），不是单据号。版本记录里带着这条操作的撤销日志（`UndoLogJson`），回退时按原动作分支处理。

| 原动作 | 回退做什么 | 注意 |
| --- | --- | --- |
| `submit`（新建） | 删除这条飞书记录 | 若记录已经不存在（已被删过），视为"已达到目标状态"，返回成功并记 `SKIPPED`，不会报错 |
| `delete`（删除） | 用快照里的字段**重建**一条记录 | 重建后的 `record_id` 与**单号都是飞书重新分配的**，原单号只在审计与撤销日志里留存；重建会另外记一条 `rebuild` 版本，便于以后再次撤销 |
| `review` / `update`（审核/修改） | 把快照里的旧值写回 | 只恢复财务可改字段以及 `状态`、`审核人`、`审批意见`；写回前按字段类型归一：`金额` 转数字、日期列转毫秒数字、文本去掉快照里的引号（否则飞书报 `1254001 WrongRequestBody` / `1254064 DatetimeFieldConvFail`） |

限制与幂等：

- 同一个版本**不能重复回退**：第二次调用返回 400，文案"该版本已经回退过（不允许重复回退）"。回退成功后会把这版标记为已回退（记录回退人与时间）。
- `submit` 分支额外存了一份"可恢复"快照，所以"回退新建 = 删除"之后仍然能把这张单重建回来。
- 版本 `kind` 必须是 `invoice`；其它类型（`file` / `dataset` / `notice`）要用各自的回退入口，调用本接口会被拒（"该版本不是报销单操作，请到相应入口回退"）。
- 回退本身也是一次高风险管理动作，会写审计 `invoice.rollback`（成功 `SUCCESS`、幂等跳过 `SKIPPED`、失败 `FAILED`）。

## 九、版本与审计

版本记录（`versions.json`）与飞书写操作一一对应，关键字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 版本号，回退接口的入参 |
| `kind` | 固定 `invoice`（报销单） |
| `operation` | `submit` / `review` / `update` / `delete` / `rebuild` / `rollback-delete` |
| `target` | `invoice:<recordId>`，前端展示时去掉前缀即为记录号 |
| `diffText` / `addedLines` / `removedLines` | 变更差异（管理后台展示用） |
| `previousBlob` / `previousHash` | 写前快照的 blob 名与摘要（回退时读它还原旧值） |
| `undoLogJson` | 撤销日志：`kind/tableId/recordId/action/fields`，回退分支由 `action` 决定 |
| `reverted` / `revertedAt` / `revertedBy` | 是否已回退、时间与操作人 |

审计动作名（写入 `App_Data/audit.jsonl`，带哈希链）：

| 动作名 | 触发点 | 结果取值 |
| --- | --- | --- |
| `invoice.submit` | 提交报销单 | `SUCCESS` / `REJECTED`（校验未通过）/ `FAILED`（飞书写失败） |
| `invoice.list` | 查询报销单列表 | `SUCCESS` / `FAILED` |
| `invoice.review` | 审核（写状态与意见） | `SUCCESS` / `FAILED` |
| `invoice.update` | 财务修改字段 | `SUCCESS` / `FAILED` |
| `invoice.delete` | 删除单据 | `SUCCESS` / `FAILED` |
| `invoice.rollback` | 按日志回退 | `SUCCESS` / `SKIPPED` / `FAILED` |

注意：`GET /api/invoice/detail` 与 `GET /api/invoice/meta` **不写审计**；只有列表查询会写 `invoice.list`。

## 十、财务工作台（`/finance`）

页面只对 `finance`、`admin`、`superadmin` 开放；其它角色登录后会看到"无权访问财务工作台"的提示面板（前端按角色拦一次，服务端权限仍会再校验一次）。

| 区域 | 能做什么 |
| --- | --- |
| 报销单列表 | 列：单号、申请人、工号、部门、报销类型、金额、票据状态、合规结果、风险摘要、状态、审核人；按状态、报销类型、部门三个下拉 + 单号/申请人关键字筛选；「刷新」重新拉取 |
| 单据详情 | 展示全部业务字段（含事由、城市、发票日期、提交时间、审批意见、审批时间、发票信息，时间戳自动格式化） |
| 审核面板 | 选择目标状态（`审核中` / `已通过` / `已驳回`）并填写 2 到 300 字意见；提交后状态、审核人、审批意见、审批时间一起写回飞书 |
| 修改面板 | 仅渲染 `financeEditableFields` 白名单字段；枚举字段（部门、报销类型、票据状态、城市、合规结果、状态）用下拉，其余用文本框；留空表示不改 |
| 高风险面板 | 有 `invoice.delete` 权限时显示「删除该报销单」（必须填删除理由）；有 `log.rollback` 权限时提示到管理后台执行回退 |
| 契约元数据 | 右侧展示服务端下发的判定口径（规则文字、可改字段、盖章字段、只读字段、金额范围） |

界面上的按钮显隐依据登录响应里的 `permissions`，但**服务端才是权威**：隐藏按钮只是减少一次注定失败的请求。

## 十一、管理后台的两个面板

### 11.1 账号管理（账号权威在本机 JSON）

| 能力 | 说明 |
| --- | --- |
| 账号列表 | 用户名、姓名、工号、角色、状态、创建时间、最后登录、飞书镜像状态 |

### 11.2 版本与回退

- 类型筛选里有「报销单」，列表展示 `kind=invoice` 的版本、差异文本与"可回退 / 已回退"标记。

- 回退成功后刷新当前面板；审计里能看到 `invoice.rollback` 记录。

## 十二、协作方接入步骤

- 准备配置：把飞书凭证写进 `AiApprovalServer/config/secrets.local.json`（结构见同目录 `secrets.local.example.json`），至少需要 `AppId`、`AppSecret`、`AppToken`，以及报销单主表的 `TableId`；账号镜像还需要 `UserTableId`。该文件已被 `.gitignore` 忽略，交付前清空即可。
- 起服务：`dotnet run`（或在 `bin/Debug/net8.0` 直接跑可执行文件），默认监听 `http://127.0.0.1:8899`。
- 拿身份：调 `POST /api/auth/login` 得到 `token` 与 `signKey`；之后所有 **POST 必须带签名**（`X-Timestamp` / `X-Nonce` / `X-Signature`，算法见 `docs/API参考.md` 第 2 章）。
- 读契约：调 `GET /api/invoice/meta` 拿到六组枚举、城市分级、金额区间、字段白名单与自身权限，用它们渲染下拉与校验，不要在前端另写一份枚举。
- 提交与查询：`POST /api/invoice/submit` → `GET /api/invoice/list` → `GET /api/invoice/detail?recordId=...`。
- 写操作失败处理：把 `code` 与 `message` 原样提示给用户；`400` 是业务校验失败（可改参数重试），`403` 是权限不足（不要重试），`429` 是限流（退避重试），`502 FEISHU_UNAVAILABLE` 表示飞书不可用（未配置或调不通）。

未配置飞书时的降级表现：

| 场景 | 表现 |
| --- | --- |
| 服务启动 | 正常启动，横幅显示"飞书镜像 未配置（跳过镜像，不影响账号功能）" |
| 账号相关 | 完全可用（登录、注册、改角色都不依赖飞书）；镜像状态为 `skipped` |
| `GET /api/invoice/list` | 502 `FEISHU_UNAVAILABLE`，`message` 为"未配置飞书凭证（config/secrets.local.json）"或"未配置报销单主表 Feishu:TableId" |
| 其它报销单接口 | 同样被拒，但走的是业务失败分支：400 `SUBMIT_REJECTED` / `REVIEW_REJECTED` / `UPDATE_REJECTED` / `DELETE_REJECTED` / `ROLLBACK_REJECTED`，`message` 与上面同源 |
| `GET /api/invoice/meta` | 仍然可用（纯本地契约，不依赖飞书） |

## 十三、排障

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 所有报销单接口返回"未配置飞书凭证" | `config/secrets.local.json` 缺失或缺 `AppId`/`AppSecret`/`AppToken` | 按模板补齐；缺文件不影响服务启动 |
| 列表可用但提交报"未配置报销单主表" | 只配了凭证，没配 `Feishu:TableId` | 填主表 `table_id`（形如 `tbl...`） |
| 502 `FEISHU_UNAVAILABLE` | 只有列表接口会用它表示飞书不可用 | 看 `message` 是"未配置"还是网络/换票失败；网络类错误会带飞书 `code/msg` |
| 写入报 `FieldNameNotFound` 一类错误 | 飞书表列名与代码不一致（多空格、少字、被改名） | 对照 `Core/InvoicePolicy.cs` 的字段常量与飞书表列名逐字核对；服务端会在写入前剔除不存在的列，因此这类错误通常意味着所有字段都被剔掉了 |
| 单选项写入失败或表里冒出奇怪选项 | 服务端枚举与飞书单选选项不一致；不要让前端自由输入枚举 | 两边同步；服务端的合法值见 `GET /api/invoice/meta` |
| 429 `RATE_LIMITED` | 提交限流（30 次/5 分钟/账号）或后台写操作限流（默认 60 次/分钟） | 退避重试；批量跑验收时临时放宽 `Limits:*` |
| 飞书返回 `Write conflict` | 同一张表并发写 | 降低并发、串行化写操作；本服务的写路径是逐条串行调用的 |
| 提交成功但单号为空 | 飞书自动编号存在极短的最终一致性延迟 | 稍后重新查询；不要在前端显示"生成中"之类的假状态 |
| 回退报"该版本已经回退过" | 同一版本只能回退一次 | 找到更早的那条版本再回退，或用重建产生的 `rebuild` 版本 |
| 回退报 `1254001 WrongRequestBody` 或 `1254064 DatetimeFieldConvFail` | 快照还原后的值与飞书列类型不一致（金额是数字列、日期列只认毫秒数字） | 服务端已按字段类型归一；若仍出现，检查飞书列类型是否被改成文本/日期以外的类型，改回数字/日期后重试 |
| 回退删除后单号变了 | 重建由飞书重新分配编号 | 属于预期行为；原单号在审计与撤销日志里可查 |
| 员工看不到自己刚提交的单 | 归属按工号匹配，历史单据缺工号时才回退姓名 | 确认账号工号与单据「工号」列一致；缺失时按姓名兜底，重名需补齐工号列 |
| 越权调用后整个 IP 被封 | 越权类操作计 2 分，默认 8 分封禁 | 管理后台「安全态势」可查看与解封；前端按权限隐藏按钮 |

## 十四、以代码为准的说明

- 归属判定优先按工号，缺工号的历史数据回退到姓名（`InvoicePolicy.BelongsTo`）；列表与详情两处都走同一个判定函数，改规则只需改一处。
- `GET /api/invoice/detail` 的实现是"拉最多 500 条记录后按 `recordId` 找"，记录量增大后应改为按记录号单条查询（`FeishuApi.GetRecordAsync` 已具备能力，当前未被报销单路径使用）。
- 报销单接口没有走"人工审批"链路：提交是员工对自己数据的写入，财务/管理员的审核与修改直接生效但全部留版本与审计。审批链路（`/api/agent/chat` 与审批后台）仍然存在，服务于其它工具。
- 字段探测结果有十分钟缓存；在飞书表里改了列名后，最迟十分钟后生效，必要时重启服务。

## 十五、真机联调检查清单（在你的机器上跑，本沙箱无法出网）

本仓库的离线验收全部跑在假飞书（`tests/mock-feishu.mjs`）上，通讯格式与真实飞书一致，但**真实网络链路必须在能出网的机器上确认一次**。
按顺序做下面四步，任何一步失败，错误信息里都会带飞书的业务 `code` 与 `msg`（不含任何凭证）：

1. 确认 .NET 能出网（这一步最容易被忽略；若这里就失败，与代码无关）：
   ```powershell
   Invoke-WebRequest -Uri 'https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal' -Method POST `
     -ContentType 'application/json' -Body '{"app_id":"x","app_secret":"y"}' -UseBasicParsing | Select-Object StatusCode
   ```
   预期 200；若报 `安全包中没有可用的凭证` / `No credentials are available in the security package`，说明本机 schannel 出网被拦，先修环境再谈业务。
2. 写凭证文件：把 `AiApprovalServer/config/secrets.local.example.json` 复制为 `config/secrets.local.json`，填四个值（`AppId` / `AppSecret` / `AppToken` / `UserTableId`）与主表 `TableId`。
3. 启动服务并只读验证（不会写任何东西）：
   ```powershell
   dotnet run --project AiApprovalServer
   # 另开一个终端：登录拿 token 后调 GET /api/invoice/meta 与 GET /api/invoice/list
   ```
   预期：`/api/invoice/meta` 返回六组枚举与 `canSeeAll`；`/api/invoice/list` 返回主表真实行（管理员可见全部，员工只见自己）。
   若返回 502 `FEISHU_UNAVAILABLE`，`message` 就是原因（凭证缺失、表 id 不对、字段名不匹配、权限不足等）。
4. 再做一次**受控写入**（建议先用一张测试表或一条明确标记的测试单）：
   提交 → 确认飞书出现新行且「工号/申请人」是登录人本人；财务审核 → 确认「状态/审核人/审批意见/审批时间」被写入；
   管理员删除 → 确认版本记录出现 `delete`；按日志回退 → 确认行被重建（单号由飞书重新分配）。

> 只读验证（第 3 步）足以证明连接、换票、字段与解析这条链路；写入验证（第 4 步）建议先在测试表上做一次，确认口径无误再切生产表。
