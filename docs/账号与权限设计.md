# 账号与权限设计

本文说明报销系统的**账号权威存储、四角色权限矩阵、人际约束、口令策略与账号生命周期**。

| 项 | 说明 |
| --- | --- |
| 权威来源 | 本机 JSON 文件 `App_Data/users.json`。**它是唯一账号权威**：登录、改密、改角色、停用、删除都只读写这个文件 |
| 飞书用户表 | 只是"让协作方看到一致数据"的镜像，允许失败、允许缺失，**不参与任何鉴权判断**（见 [飞书镜像对接.md](飞书镜像对接.md)） |
| 策略代码 | 权限矩阵与人际约束在 `AiApprovalServer/Core/AccountPolicy.cs`；角色常量与标签在 `Core/Models.cs`（`Roles`）；账号读写与策略执行在 `Services/UserService.cs`；口令散列在 `Security/Crypto.cs` |
| 接口 | 见 [API参考.md](API参考.md) 第 4 章（鉴权与账号）与 7.2（账号管理） |
| 本文口径 | 所有行为描述均取自上述源码；无法从代码确认的地方标注「以代码为准」，不做推测 |

## 1. 账号数据结构

`App_Data/users.json` 是一个 JSON 数组，每个元素对应一个账号（`Core/Models.cs` 的 `UserRecord`）。
所有写操作都走 `Core/JsonStore.cs` 的原子写（临时文件 + 替换）与文件级互斥锁。

| 字段 | 类型 | 语义与约束 |
| --- | --- | --- |
| `id` | string | 账号主键，形如 `u_` + 12 位十六进制（`"u_" + Crypto.RandomHex(6)`），服务端生成 |
| `userName` | string | 登录名。3-32 位，只允许字母、数字、下划线、点、短横线；**唯一性按大小写不敏感比较** |
| `displayName` | string | 姓名（报销单「申请人」的取值来源）。留空则取用户名，最长截断到 32 字符 |
| `role` | string | 四角色之一：`superadmin` / `admin` / `finance` / `employee` |
| `employeeId` | string | 工号，`E` + 4 位数字（如 `E0001`）。服务端生成、不可自填，与飞书报销单「工号」列一致 |
| `passwordHash` | string | PBKDF2-HMAC-SHA256 摘要，base64（32 字节输出） |
| `passwordSalt` | string | 每账号独立的 16 字节随机盐，base64 |
| `passwordIterations` | int | 迭代次数。界面/接口创建的账号取 `Security:PasswordIterations`（默认 **1200000**）；从飞书用户表导入且本人还没登录过的账号按导入时的 `Feishu:MirrorPbkdf2Iterations`（默认 100000）记录，登录成功后自动升级为当前方案（见 [飞书镜像对接.md](飞书镜像对接.md)） |
| `mirrorPasswordCipher` | string | 飞书镜像用的**演示口令**密文（AES-256-GCM），AAD 为 `mirror-demo-password:<userId>`；真实口令不落这里 |
| `mirrorState` | string | 镜像状态，默认 `pending`：`pending` / `synced` / `failed` / `skipped` |
| `mirrorError` | string | 镜像失败原因（写入时截断到 300 字符） |
| `mirrorAt` | datetime? | 最近一次镜像尝试时间（UTC） |
| `mirrorRecordId` | string | 飞书用户表里对应行的 `record_id`，更新镜像时用它定位 |
| `mirrorHashHex` / `mirrorSaltHex` | string | **实际写进飞书用户表**的哈希与盐（十六进制）。demo 模式下它们是演示口令的材料 |
| `emailCipher` | string | 邮箱密文（AES-256-GCM），AAD 为 `aiapproval:user-email:<userId>`；可选字段 |
| `emailMasked` | string | 邮箱掩码，用于界面展示（例如 `ab****@example.com`） |
| `disabled` | bool | 停用标记。为真时登录直接拒绝（先于口令校验） |
| `failedLoginCount` | int | 连续登录失败计数（成功登录后清零） |
| `lockedUntil` | datetime? | 锁定截止时间（UTC）。`IsLocked` = 该时间晚于当前时间 |
| `createdAt` | datetime | 创建时间（UTC） |
| `createdBy` | string | 创建者用户名；系统播种时为 `seed`，模型默认值为 `system` |
| `lastLoginAt` / `lastLoginIp` | datetime? / string | 最近一次成功登录的时间与来源 IP |
| `aiQuotaDate` / `aiCallsToday` | string / int | AI 每日调用配额（防刷接口烧钱），跨天自动重置 |
| `tokenEpoch` | int | **令牌世代**，见下节 |
| `origin` | string | 账号来源，见 1.3 |

### 1.1 口令散列参数（`Security/Crypto.cs`）

| 项 | 取值 |
| --- | --- |
| 算法 | PBKDF2-HMAC-SHA256（`Rfc2898DeriveBytes.Pbkdf2`，不用已淘汰的 MD5/SHA1） |
| 迭代次数 | `Security:PasswordIterations` = 1200000（环境变量 `AISERVER_PASSWORD_ITERATIONS`） |
| 盐 | 每账号 16 字节随机（`RandomNumberGenerator`），base64 存储 |
| 输出 | 32 字节摘要，base64 存储 |
| 校验 | `CryptographicOperations.FixedTimeEquals` 恒定时间比较 |
| 账号不存在时 | 仍执行一次等价 PBKDF2（`dummy: true`），抹平"用户是否存在"的响应时间差 |

### 1.2 令牌世代 `tokenEpoch` 的作用

访问令牌（JWT）载荷里带一个世代号 `epo`，取自签发时的 `tokenEpoch`。
安全中间件每次请求都比对 `user.tokenEpoch` 与令牌里的 `epo`，不一致即返回 `401 TOKEN_STALE`（审计 `auth.token`）。

因此**改密、改角色、停用/启用、旧角色迁移**都会让该账号**已经签发的全部令牌立即失效**，
用户必须重新登录；这是"改完权限后旧会话不能继续用旧权限"的实现方式，不依赖令牌过期时间。

> 服务端没有令牌吊销列表（无黑名单存储）；登出只写审计并提示客户端自行清除本地令牌，令牌会在过期或世代变更前继续有效（见 [API参考.md](API参考.md) 4.2）。

### 1.3 账号来源 `origin`

`origin` 记录"这个账号是怎么来的"，只用于后台展示与排查，**不参与任何权限判断**（权限只看 `role`）。旧数据没有该字段时按默认值 `local` 处理。

| `origin` | 含义 | 产生路径 |
| --- | --- | --- |
| `local` | 本机创建（默认值） | `POST /api/admin/users`、`POST /api/auth/register` 以及历史数据 |
| `feishu-sync` | 从飞书用户表导入 | `POST /api/admin/users/sync-from-feishu` 中 `action = created` 的账号（见第 10 节） |
| `bootstrap` | 初始超级管理员 | `Bootstrap:Admin` 配置播种（见第 9 节） |

`GET /api/admin/users` 会把 `origin` 一并返回，便于在后台区分"本机自建"与"对面导入"。
注意它**不代表账号的信任级别**：从对面导入的账号在通过口令校验后，就是一个普通的 `admin` / `finance` / `employee`，它的权限完全由本机 `role` 决定。

## 2. 四角色与权限矩阵

角色常量（`Core/Models.cs` → `Roles`）：

| 角色键 | 标签（`Roles.Label`） | 定位 |
| --- | --- | --- |
| `superadmin` | 超级管理员 | 账号面最大：可授予/撤销管理员、可删除账号 |
| `admin` | 管理员 | 业务面与超管相同；账号面不能授予管理员、不能删账号 |
| `finance` | 财务部 | 可查全部报销单、可审核与修改；不能删除、不能回退、不能管账号 |
| `employee` | 员工 | 只能提交报销单、只能查自己的单 |

权限矩阵（`Core/AccountPolicy.cs` → `AccountPolicy.Matrix`，逐条对照）：

| 权限键 | 中文标签（`Permissions.Label`） | superadmin | admin | finance | employee |
| --- | --- | :--: | :--: | :--: | :--: |
| `auth.login` | （无标签，回退为键名本身） | 是 | 是 | 是 | 是 |
| `account.create` | 创建账号（注册） | 是 | 是 | — | — |
| `account.list` | 查看账号列表 | 是 | 是 | — | — |
| `account.manage` | 维护账号（改角色/停用/重置口令） | 是 | 是 | — | — |
| `account.grant_admin` | 授予或撤销管理员 | **是** | — | — | — |
| `account.delete` | 删除账号 | **是** | — | — | — |
| `invoice.read.self` | 查询自己的报销单 | 是 | 是 | 是 | 是 |
| `invoice.read.all` | 查询全部报销单 | 是 | 是 | 是 | — |
| `invoice.submit` | 提交报销单 | 是 | 是 | 是 | 是 |
| `invoice.review` | 审核报销单 | 是 | 是 | 是 | — |
| `invoice.update` | 修改报销单 | 是 | 是 | 是 | — |
| `invoice.delete` | 删除报销单 | 是 | 是 | — | — |
| `log.read` | 查看操作日志 | 是 | 是 | 是 | — |
| `log.rollback` | 按日志回退操作 | 是 | 是 | — | — |
| `admin.read` | 管理端只读分析 | 是 | 是 | — | — |

读法：
- 岗位权限键（`invoice.*` / `log.*`）是**业务面**，超管与管理员完全相同，差别只在账号面。
- **能进管理后台的是超管与管理员**：安全中间件对 `/api/admin/*` 的判定是 `Roles.IsAdminSide(role)`（`superadmin` 或 `admin`）；财务与员工访问会被 `403 FORBIDDEN` 拦下并记 3 分。
- 财务是"能审核、能改、不能删、不能回退"。
- 员工只有三条：登录、查自己、提交。

> 业务工具面另有一套权限键（`Tools/ToolCatalog.cs` → `Permissions` 与 `RolePermissions`，覆盖文件、数据集、通知等），
> 与本文的账号权限键并存：`ToolCatalog` 决定"某个角色能用哪些工具"，`AccountPolicy` 决定"某个角色能对账号做什么"。

## 3. 人际约束（谁能对谁做什么）

全部判定集中在 `Core/AccountPolicy.cs`，每个方法返回 `null` 表示允许，否则返回**拒绝原因字符串**（接口直接把它作为 `message` 回给调用方，并写入审计）。判定顺序即代码中的书写顺序。

### 3.1 创建账号 `CanCreateAccount(actorRole, targetRole)`

| 顺序 | 条件 | 拒绝文案 |
| --- | --- | --- |
| 1 | 操作者没有 `account.create` | 当前角色无权创建账号 |
| 2 | 目标角色不是四角色之一 | 目标角色非法 |
| 3 | 目标角色为 `superadmin` | 超级管理员账号只能由系统初始化，不能在界面上创建 |
| 4 | 目标角色为 `admin` 且操作者没有 `account.grant_admin` | 只有超级管理员可以创建管理员账号 |

### 3.2 变更角色 `CanChangeRole(actorRole, actorId, targetId, targetCurrentRole, newRole, superAdminCount)`

| 顺序 | 条件 | 拒绝文案 |
| --- | --- | --- |
| 1 | 新角色不是四角色之一 | 目标角色非法 |
| 2 | 操作者与目标**是同一个账号** | 不能修改自己的角色（避免自我提权） |
| 3 | 新角色为 `superadmin` 且目标当前不是超管 | 超级管理员角色只能由系统初始化，不能通过接口授予 |
| 4 | 新旧任一侧涉及 `admin`，或目标当前是 `superadmin`，且操作者没有 `account.grant_admin` | 只有超级管理员可以授予或撤销管理员/超级管理员 |
| 5 | 目标当前是 `superadmin`、新角色不是 `superadmin`，且当前可用超管数 ≤ 1 | 系统必须保留至少一个超级管理员 |
| 6 | 操作者既没有 `account.manage` 也没有 `account.grant_admin` | 当前角色无权变更他人角色 |

`superAdminCount` 由 `UserService.CountActiveSuperAdminsAsync()` 计算：角色为 `superadmin` **且未停用**的账号数。

### 3.3 停用 / 启用 `CanSetDisabled(actorRole, actorId, targetId, targetRole, disable, superAdminCount)`

| 顺序 | 条件 | 拒绝文案 |
| --- | --- | --- |
| 1 | 操作者没有 `account.manage` | 当前角色无权停用或启用账号 |
| 2 | 目标是**启用**（`disable = false`） | 直接允许 |
| 3 | 操作者与目标是同一个账号 | 不能停用自己的账号 |
| 4 | 目标是 `superadmin` 且当前可用超管数 ≤ 1 | 系统必须保留至少一个超级管理员 |

### 3.4 重置他人口令 `CanResetPassword(actorRole, actorId, targetId, targetRole)`

| 顺序 | 条件 | 拒绝文案 |
| --- | --- | --- |
| 1 | 操作者与目标是同一个账号 | 直接允许（改自己的口令走 `POST /api/auth/password`） |
| 2 | 操作者没有 `account.manage` | 当前角色无权重置他人口令 |
| 3 | 目标是 `superadmin` 且操作者不是 `superadmin` | 只有超级管理员可以重置超级管理员的口令 |

### 3.5 删除账号 `CanDeleteAccount(actorRole, actorId, targetId, targetRole, superAdminCount)`

| 顺序 | 条件 | 拒绝文案 |
| --- | --- | --- |
| 1 | 操作者没有 `account.delete`（只有超管有） | 只有超级管理员可以删除账号 |
| 2 | 操作者与目标是同一个账号 | 不能删除自己的账号 |
| 3 | 目标是 `superadmin` 且当前可用超管数 ≤ 1 | 系统必须保留至少一个超级管理员 |

### 3.6 约束背后的原因

- **不能改自己的角色 / 不能停用自己 / 不能删自己**：阻断"自我提权"与"自锁"两类事故。提权必须由另一个更高权限账号完成，留痕且可追责。
- **必须保留最后一个超管**：超管是唯一能授予管理员与删除账号的角色；如果连它都被降级或停用，系统会永久失去账号管理能力，只能改文件恢复。
- **超管账号只能系统初始化**：超管既不能用创建接口生成（`CanCreateAccount` 第 3 条），也不能用改角色接口把已有账号提升为超管（`CanChangeRole` 第 3 条），
  避免"超管自我复制"——得到超管的途径只有三种：配置播种初始超管（第 9 节）、全新数据根的演示账号播种、直接编辑 `users.json`。从飞书用户表导入**不会**产生超管（第 10 节）。
- **管理员不能重置超管口令**：否则管理员可以用一次"重置口令"接管整个系统，绕过权限矩阵。

## 4. 工号分配与唯一性

分配实现：`UserService.NextEmployeeId(IEnumerable<string> existingIds)`。

| 规则 | 说明 |
| --- | --- |
| 格式 | `E` + 4 位十进制（`D4` 补零），例如 `E0001`、`E0042` |
| 取值 | 遍历传入的既有工号，识别"长度 5、首字符 E/e、后 4 位可解析为整数"的值，取**最大值 + 1** |
| 上限 | 最大值达到 9999 时抛 `InvalidOperationException("工号已用尽（E9999）")` |
| 分配时机 | 创建账号时在 `JsonStore` 的文件级锁内分配（`MutateAsync` 回调里），避免两个并发创建拿到同一个号 |
| 回填 | 启动时 `BackfillEmployeeIdsAsync` 给缺失工号的历史账号补号（早期版本没有该字段） |
| 不可自填 | 创建接口不接收工号参数，工号一律服务端生成 |

**唯一性的边界（以代码为准）**：唯一性来自"同一份账号列表快照上的最大值 + 1"＋文件级锁串行化写入。
`users.json` 没有数据库唯一索引，删除账号后其工号会被后续新账号复用（例如删掉 `E0002`，下一个新账号仍可能拿到 `E0002`）；
工号与历史报销单的对应关系只在飞书表里，因此**已删除账号的工号可能在新账号上重复出现**。

## 5. 账号生命周期

| 动作 | 入口 | 对 `users.json` 的写入 | `tokenEpoch` | 审计动作 | 是否触发飞书镜像 |
| --- | --- | --- | --- | --- | --- |
| 创建 | `POST /api/auth/register` 或 `POST /api/admin/users` | 新增一条记录（分配工号、写入口令散列、`origin = local`） | 新账号从 0 开始 | `user.create`（`AuthApi` 写 `auth.register`） | 是（带明文口令，用于生成演示口令） |
| 初始超管播种 | 启动时按 `Bootstrap:Admin` 配置执行（`SeedBootstrapSuperAdminAsync`） | 只在该用户名不存在时新增一条记录（角色 `superadmin`、`origin = bootstrap`、`mirrorState = skipped`）；已存在时最多补工号 | 新账号从 0 开始 | `system.bootstrap-admin` | 否（有意不镜像） |
| 从飞书同步账号 | `POST /api/admin/users/sync-from-feishu` | 只新增本机没有的账号（`origin = feishu-sync`），或给已有账号补 `record_id` | 新账号从 0 开始；已有账号不变 | `user.sync-feishu` | 否（方向相反：从对面读进本机） |
| 登录成功 | `POST /api/auth/login` | 失败计数清零、解除锁定、写 `lastLoginAt` / `lastLoginIp` | 不变 | `auth.login`（`SUCCESS`） | 否 |
| 登录失败 | `POST /api/auth/login` | 失败计数 +1；达阈值则写 `lockedUntil` 并把计数清零 | 不变 | `auth.login`（`FAIL`）；达阈值另写 `auth.lockout` | 否 |
| 修改自己的口令 | `POST /api/auth/password` | 新散列 + 新盐；失败计数与锁定清零；**清空镜像口令字段** | +1 | `user.password` | 是（用新口令重新生成演示口令） |
| 重置他人口令 | `POST /api/admin/users/{id}/reset-password` | 同上 | +1 | `user.password` | 是（同上） |
| 变更角色 | `POST /api/admin/users/{id}/role` | 改 `role` | +1 | `user.role` | 是（同步新角色标签） |
| 停用 / 启用 | `POST /api/admin/users/{id}/status` | 改 `disabled` | +1 | `user.disable` / `user.enable` | 是（同步「账号状态」列） |
| 删除 | `POST /api/admin/users/{id}/delete` | 从数组中移除该记录 | 记录已不存在 | `user.delete` | 否（飞书镜像行需人工清理） |
| 旧角色迁移 | 启动时自动执行 | 改 `role`、补 `employeeId` | +1（仅角色真的变化时） | `system.migrate-roles` | 否 |

补充说明：
- 删除账号只删除本机权威记录，**不会**删除该账号的工作区目录（`UserService.DeleteAsync` 只操作 `users.json`；工作区清理以代码为准），也不会删除飞书用户表里的镜像行。
- 登录**不会**回写飞书（镜像只在创建、改密、改角色、停用/启用、手动重试时触发），因此飞书表里的「最后登录时间」可能落后于本机。
- 所有账号写操作都在 `JsonStore` 的文件级锁内完成；飞书写入在锁外执行（避免网络耗时占着文件锁）。

## 6. 口令策略与登录锁定

### 6.1 口令与用户名校验（`UserService.ValidatePassword` / `ValidateUserName`）

| 规则 | 具体判定 | 不满足时的提示 |
| --- | --- | --- |
| 长度下限 | 至少 10 位 | 口令长度至少 10 位 |
| 长度上限 | 不超过 128 位 | 口令长度不得超过 128 位 |
| 字符类别 | 大写字母 / 小写字母 / 数字 / 非字母数字 四类中至少满足三类 | 口令需至少包含大写字母、小写字母、数字、符号中的三类 |
| 常见弱口令 | 小写化后不得包含以下片段：`password`、`12345678`、`qwerty`、`admin123`、`admin888`、`letmein`、`iloveyou`、`passw0rd`、`123456789`、`1qaz2wsx`、`abc123456`、`admin@123` | 口令包含常见弱口令片段 |
| 不得含用户名 | 口令小写化后不得包含用户名（用户名也小写化） | 口令不得包含用户名 |
| 不得含 admin | 口令小写化后不得包含 `admin`（除非用户名本身就是 `admin`） | 口令不得包含 admin |
| 用户名格式 | 3-32 位，只允许字母、数字、下划线、点、短横线 | 用户名必须为 3-32 位，只允许字母、数字、下划线、点、短横线 |
| 邮箱（可选字段） | 形如 `local@domain.tld`（正则见 `UserService.EmailRx`） | 邮箱格式非法 |

> 「不得包含用户名」这条规则很严格：它按**子串**匹配（例如用户名为 `root` 时，口令里任何位置出现 `root` 都会被拒）。
> 给账号起名或设口令时要注意这一点——播种子口令正是按这条规则挑选的（见第 8 节）。

### 6.2 登录失败与锁定

| 维度 | 阈值来源 | 默认值 | 触发结果 |
| --- | --- | --- | --- |
| 来源 IP | `Limits:LoginPerFiveMinutesPerIp` | 120 次 / 5 分钟 | `429 RATE_LIMITED`（同时给该 IP 记 1 分），审计 `auth.rate-limit` |
| **(来源 IP + 账号) 组合** | `Limits:LoginPerFifteenMinutesPerAccount` | 5 次 / 15 分钟 | 达到后锁定该**组合** `Limits:AccountLockMinutes`；审计 `auth.lockout` |
| 组合锁定时长 | `Limits:AccountLockMinutes` | 15 分钟 | 锁定期内**该来源用正确口令也被拒**（401 `AUTH_LOCKED`），其他来源/其他账号不受影响 |

> **为什么按 (IP + 账号) 而不是按账号**：按账号全局锁定会让攻击者用 5 次错误口令把任意人（含管理员）锁在门外，成本极低且配合用户名枚举可精准打击。
> 改成组合键后，攻击者只能锁死"自己这条来源 IP 对某个账号"的通道，等同自残；真正的暴力破解仍由**来源 IP 限流 + WAF 计分封禁**兜住。

防用户名枚举的组合：
- **账号不存在、账号被停用、口令错误 三条路径都只执行一次等价的 PBKDF2**（不存在/停用走 `dummy: true`，算完即弃），响应时间不可区分；
- 失败响应统一固定延迟；
- 账号不存在与口令错误返回**同一句**文案 `用户名或口令错误`；
- 账号被停用返回 `该账号已被禁用，请联系管理员`（该判断在哈希之后，避免"停用账号响应更快"再次泄露信息）。

失败计数与锁定状态**都在进程内存**（重启即清零）；`users.json` 里的 `failedLoginCount` 仅作审计留痕，`lockedUntil` 字段已不再作为门禁。

## 7. 旧角色迁移

旧版本使用三角色（`user` / `staff` / `admin`），新版本为四角色。映射关系（`Roles.Migrate`）：

| 旧角色 | 新角色 | 说明 |
| --- | --- | --- |
| `user` | `employee` | 旧「用户」，只能看自己的数据 |
| `staff` | `finance` | 旧「员工」（当时是能看全部数据的乙方角色，语义上对应财务） |
| `admin` | `admin` | 保持不变 |

执行时机与行为（`UserService.MigrateLegacyAsync`，由 `EnsureSeedAsync` 在每次启动时首先调用）：

- 遍历全部账号，按上表改写 `role`；**只有在角色真的变化时**才 `tokenEpoch++`（旧令牌立即失效）。
- 同时给缺 `employeeId` 的账号补工号。
- 有任何迁移发生时写一条审计：`system.migrate-roles`（`actor = system`），明细形如 `employee：用户（旧） → 员工`。
- `Roles.Label` 仍为旧角色保留了显示名 `用户（旧）` / `员工（旧）`，仅用于迁移期展示与历史数据处理。

## 9. 初始超级管理员引导

超管是唯一能授予管理员、删除账号的角色（第 2 节），而本系统**不允许通过界面创建超管**（第 3 节的三条约束都指向"防超管自我复制"）。
于是全新部署会撞上一个死锁：没有任何账号能进管理后台，也就没有人能授予第一个管理员。解决办法不是给界面开口子，而是把"第一个超管"交给部署配置播种。

配置来源（`Core/AppConfig.cs` → `LoadBootstrapAdmin`，自上而下取第一个非空值）：

| 顺序 | 来源 | 形如 |
| --- | --- | --- |
| 1 | 环境变量 | `AISERVER_BOOTSTRAP_USERNAME`、`AISERVER_BOOTSTRAP_PASSWORDHASH`、`AISERVER_BOOTSTRAP_PASSWORDSALT`、`AISERVER_BOOTSTRAP_PASSWORD`、`AISERVER_BOOTSTRAP_DISPLAYNAME`、`AISERVER_BOOTSTRAP_ENABLED`、`AISERVER_BOOTSTRAP_PASSWORDITERATIONS` |
| 2 | 本地密钥文件 | `config/secrets.local.json` 的 `BootstrapAdmin` 段（该文件已被 `.gitignore` 忽略） |
| 3 | 配置文件 | `appsettings.json` 的 `Bootstrap:Admin:*` |

仓库自带的默认值是 `xinghan`（姓名「星涵」）配口令 `Ss@123456`，写在 `appsettings.json` 里（只放哈希，不放明文），这样全新克隆开箱就能登进管理后台。
**这是公开的演示口令，首次登录后必须立刻改掉**；不想用它就把 `Bootstrap:Admin:Enabled` 置为 `false`，改用环境变量或本机密钥文件播种自己的账号。

可用键：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `Enabled` | `true` | 置 `false`（或删除整段配置）即不再播种，**不会因此启动失败** |
| `UserName` | 空 | 初始超管的登录名。**允许中文**——不走注册用的 ASCII 用户名校验；为空时记一条启动警告并跳过播种 |
| `DisplayName` | 取 `UserName` | 姓名（报销单「申请人」的取值来源），截断 32 字符 |
| `PasswordHash` / `PasswordSalt` | 空 | base64 的 PBKDF2-HMAC-SHA256 摘要与盐，**推荐只填这两项**：配置文件里不出现明文 |
| `Password` | 空 | 明文口令，仅在没有哈希时才用：播种那一次会算成哈希写进 `users.json`，之后配置里的明文不再被读取 |
| `PasswordIterations` | `210000` | 预计算哈希所用的迭代次数；只给明文时按 `Security:PasswordIterations`（默认 120 万次）计算。预计算哈希按不带服务端密钥的旧方案校验，首次登录后自动升级 |

口令两条给法的对照：

| 给法 | 配置里出现什么 | 行为 |
| --- | --- | --- |
| `PasswordHash` + `PasswordSalt`（推荐） | 只有 base64 摘要与盐 | 直接写进 `users.json`；任一不是合法 base64 时记一条启动警告并忽略该哈希（回落到明文，或跳过播种） |
| 只给 `Password` | 明文口令 | 仅在播种那一次用 PBKDF2 算成哈希（21 万次迭代、32 字节输出、16 字节随机盐）落盘；此配置里的明文从此不再被读取 |
| 两者都没给 | —— | 记一条启动警告并跳过播种，服务照常启动 |

行为边界：

| 事项 | 行为 |
| --- | --- |
| 创建时机 | 只在账号库里**不存在**该用户名时创建一次（用户名按大小写不敏感比较）；已存在时最多补一个缺失的工号，**绝不回写口令或角色** |
| 会不会"复活" | 不会。初始超管建出来之后就是普通账号：改口令、改角色、停用、删除都照常生效，**重启不会把它改回来** |
| 与演示账号的先后 | 播种顺序在四个演示账号**之后**——演示账号只在"账号库为空"时创建，先建超管会让那次判断落空，四个演示账号就永远不会出现 |
| 飞书镜像 | **不写飞书用户表**：对面没有超管这一档，也没有必要让初始凭据经由第三方表单流转。该账号的 `mirrorState` 直接写为 `skipped`，`mirrorError` 说明"初始超级管理员不镜像" |
| 口令强度 | **不套用注册的强口令策略**（第 6 节）。因此初始口令必须在首次登录后立刻改成强口令 |
| 审计 | `system.bootstrap-admin`（`outcome = SUCCESS`，`actor` 为 `system`，明细含工号与"口令取自 Bootstrap:Admin 配置"） |
| 启动提示 | 创建成功时横幅打印 ` [初始超管] …已创建，口令来自 BootstrapAdmin 配置——首次登录后请立刻改成强口令，并在交付/上传前清空 config/secrets.local.json 里的 BootstrapAdmin 段`；配置有问题（`UserName` 为空、哈希不是 base64、既无哈希也无明文）时打印 ` [提示] …` 警告 |
| 明文口令的额外警告 | 只填了明文 `Password` 时额外打印一条提示，要求确认这段配置不在会提交/交付的文件里（需要预计算哈希时，可用仓库自带的本地小工具 `node tools/hash-password.mjs <口令> [迭代次数]` 生成 `PasswordHash` 与 `PasswordSalt`，它按服务端同一口径计算、不联网、不落盘） |

配置样例（`config/secrets.local.json`，全部为占位值，真实值自行生成）：

```json
{
  "BootstrapAdmin": {
    "Enabled": true,
    "UserName": "ops-admin",
    "DisplayName": "运维管理员",
    "PasswordHash": "<在 config/secrets.local.json 中填写 base64 摘要>",
    "PasswordSalt": "<在 config/secrets.local.json 中填写 base64 盐>",
    "PasswordIterations": 210000
  }
}
```

> 交付与上传：`BootstrapAdmin` 段在播种完成后已无用处（账号已经落在 `users.json` 里），**交付/上传前请清空该段**——清空既不影响启动，也不影响已经建出来的账号。

## 10. 飞书账号同步（管理端手工触发）

协作方的账号已经在飞书用户表里，并且他们用自己的前端登录。接管本系统时不必把口令重发一遍：把对面已有的账号补进本机库即可，对方的原口令照样能用。

| 动作 | 接口 | 需要的权限键 | 说明 |
| --- | --- | --- | --- |
| 只读预览 | `GET /api/admin/users/feishu-rows` | `account.list` | 看清对面有哪些行、与本机是否重合；**响应里不含口令哈希**；未配置飞书时返回 `configured = false` 与说明文案 |
| 执行同步 | `POST /api/admin/users/sync-from-feishu` | `account.create` | 请求体 `{ dryRun, reason }`；受后台写操作限流；未配置飞书或从对面读到 0 行 → 409 `SYNC_UNAVAILABLE` |

本机权威原则（这是整节最重要的一条）：

| 场景 | 处置 |
| --- | --- |
| 本机没有这个账号 | 新建（`action = created`），`origin = feishu-sync` |
| 本机已有、但本机缺 `record_id` | **认领**对面的那一行（`action = adopted`）：只记下 `record_id`，之后本机改角色/停用会更新到那一行，而不是再建一行重复账号 |
| 本机已有、且本机已有 `record_id` | 不动（`action = exists`）：**口令、角色、启停一律保持本机值** |
| 这一行不可用，或操作者无权创建该角色 | 跳过（`action = skipped`），原因写在该行的 `detail` |

> 为什么"只补不改"：飞书用户表是协作方可以直接编辑、导出、共享的多维表格。如果同步会覆盖本机账号，那么"在对面表里改一行"就等于改本系统的管理员；
> 反过来，让本机永不被外部表改写，攻击面就收敛成"对面多出来的行只能新增账号，且新增的角色还要过权限矩阵"。

角色映射与边界：

| 对面「角色」列 | 本系统角色 |
| --- | --- |
| 管理员 | `admin` |
| 财务 | `finance` |
| 员工 / 空 / 其它任何值 | `employee` |

- 映射实现是 `Roles.FromFeishuLabel`（含"管理"→ `admin`、含"财务"→ `finance`、其余 → `employee`）。
- **对面的「管理员」永远不会变成本系统的超管**：对面那张表没有超管这一档，超管只能由配置播种（第 9 节）或直接编辑 `users.json` 得到。
- **权限矩阵优先于同步**：新建每一行之前都会走 `AccountPolicy.CanCreateAccount(操作者角色, 目标角色)`，操作者无权创建的角色逐行跳过并写明原因（例如普通管理员不能通过同步造出管理员账号）。同步因此不会变成提权通道。

口令与工号的口径：

| 项 | 口径 |
| --- | --- |
| 对面口令材料 | 十六进制编码的 PBKDF2-HMAC-SHA256，迭代次数与协作方一致（`Feishu:MirrorPbkdf2Iterations`，默认 100000） |
| 导入转换 | 按十六进制解码后转成 base64 存入 `passwordHash` / `passwordSalt`，并把该账号的 `passwordIterations` 记为同一个迭代次数；登录校验按账号自己的这个值走，所以**对方用他在对面前端用的原口令就能登录本系统** |
| 对面没有可用哈希 | 账号照样建，但标记 `needsPasswordReset = true`；管理员重置口令前登不进来（本机不会给出空口令入口） |
| 工号 | 对面工号格式合法（`E` + 四位数字）且不与本机冲突时沿用（报销单靠工号认人，两边必须一致）；冲突或没填则由本机新发（第 4 节） |
| 姓名 | 对面「姓名」为空时取用户名 |
| 时间与状态 | 创建时间、最后登录时间沿用对面的值；对面标了「停用」的行，导入时本机同样置为停用 |

审计与留痕：`user.sync-feishu`——预览记 `PREVIEW`、执行记 `SUCCESS`、从对面读到 0 行记 `FAIL`、无 `account.create` 权限记 `DENIED`；明细里带"读到 / 新建 / 认领 / 已存在 / 跳过 / 待重置口令"六个计数，便于对账。

> 建议的操作顺序：先用 `GET /api/admin/users/feishu-rows` 看清对面有哪些行，再用 `dryRun = true` 预览一次，确认 `created` / `adopted` / `skipped` 与预期一致后再执行；
> 执行完在 `GET /api/admin/users` 里按 `origin = feishu-sync` 复核新账号的工号与角色。

## 12. 以代码为准的说明与运维提示

以下条目是核对源码（并在本机运行验证）后确认的**当前实现现状**，与设计意图或历史文档不一致，使用前请注意：

1. **账号数量无分页**：`UserService.AllAsync()` 每次全量读取 `users.json`，账号量大时账号列表接口与"最后一个超管"计数都会全量扫描（以代码为准）。
2. **删除账号不清理工作区目录，也不清理飞书镜像行**：接口响应里已明确提示"飞书镜像行需人工清理"；工作区目录同样不会随账号删除而移除。
3. **工号可被复用**：唯一性来自"同一份账号列表快照上的最大值 + 1"与文件级锁串行化，`users.json` 没有数据库唯一索引；
   删除账号后其工号会被后续新账号复用（例如删掉 `E0002`，下一个新账号仍可能拿到 `E0002`）。
4. **未配置飞书时镜像"跳过"不会落盘**：`UserService.MirrorAsync` 在 `FeishuMirror.Enabled` 为假时直接返回 `skipped`，
   不经过 `PersistMirrorStateAsync`，因此：
   - 创建账号的接口响应里 `mirrorState = "skipped"`、`mirrorNote` 为"未配置飞书，已跳过镜像"；
   - 但 `users.json` 里该账号的 `mirrorState` 仍是初始值 `"pending"`（实测：未配置飞书播种出的四个账号都是 `pending`）。
   两处口径不一致，以代码为准；管理端看到 `pending` 属正常现象。
5. **`Security:AllowSelfRegistration` 与 `Security:SelfRegistrationPerHourPerIp` 是展示用遗留配置**：
   注册已收敛为"需要登录 + `account.create` 权限"（即注册 = 管理员行为），这两个配置项只被 `GET /api/public/health` 读取展示，
   不再参与注册门禁；注册接口自身的限流是硬编码的 **20 次/小时/操作者账号**（限流键 `register:user:<userId>`）。
   这是刻意的收敛，而不是漏接线。
6. **改角色、停用/启用与重置口令的请求模型里带 `reason` 字段**，但只有改角色接口会校验它（少于 2 个字符 → 400 `REASON_REQUIRED`）；
   停用/启用与重置口令当前不读取该字段（以代码为准）。
7. **拒绝类操作会计入攻击计分**：越权创建账号（`auth.register` 被策略拒绝）与越权改角色各给来源 IP 记 **2 分**
   （`SecurityGuard.Strike(..., weight: 2, waf: true)`），非管理员访问 `/api/admin/*` 记 3 分，默认封禁阈值 `Limits:WafStrikesBeforeBan` 为 8 分。
   **用脚本连着跑越权用例时，请临时放宽该阈值**（例如环境变量 `Limits__WafStrikesBeforeBan=40`），否则本机会被自动封禁、后续用例全变成 403。
8. **登录维度限流默认 6 次/5 分钟/IP**（`Limits:LoginPerFiveMinutesPerIp`），账号维度连续失败 5 次锁定 15 分钟。
   批量验收登录流程时需要放宽这两个阈值（`Limits__LoginPerFiveMinutesPerIp` / `Limits__LoginPerFifteenMinutesPerAccount`），
   否则会撞 429 或把演示账号锁住。
