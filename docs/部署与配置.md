## 一、运行环境要求

| 项目 | 要求 | 说明 |
| --- | --- | --- |
| .NET | **.NET 8 SDK**（构建）/ .NET 8 运行时（仅运行） | 目标框架 `net8.0`；更高版本 SDK 也可构建 net8.0 项目 |
| 第三方 NuGet 依赖 | **零** | 项目没有任何 `PackageReference`；JWT、PBKDF2、AES-GCM 全部用 .NET 内置实现 |
| 操作系统 | Windows / Linux / macOS | 未使用 Windows 专有 API；文件权限收紧在非 Windows 上走 `File.SetUnixFileMode` |
| 数据库 | **不需要** | JSON 文件即数据库，落盘在数据目录 |
| Node.js | **不需要**（仅跑验收套件时需要 18+） | 服务本身是纯 .NET 应用 |
| 反向代理 | 可选 | 仅在需要对外暴露时使用；本服务自身不配置 TLS 证书 |
| 全球化支持 | 无需 ICU | csproj 设置了 `InvariantGlobalization=true`，精简镜像/容器可直接运行 |

端口与网络默认姿态：**只监听回环 `http://127.0.0.1:8899`**，不对外网暴露；对外提供时见第九节。

## 二、构建与启动

### 2.1 构建

工作目录是应用目录 `AiApprovalServer/`：

```bash
cd AiApprovalServer

# 开发/本地运行：构建 Debug
dotnet build

# 发布包：Release + 指定输出目录
dotnet publish -c Release -o ./out
```

`wwwroot`（三个前端页面）由 csproj 自动复制到输出目录，**不需要额外拷贝静态文件**，也不需要为了出页面而特地 publish。

### 2.2 启动

```bash
cd AiApprovalServer
dotnet run
```

或者运行构建/发布产物（Windows 为 `AiApprovalServer.exe`，Linux/macOS 为 `AiApprovalServer`）：

```bash
./out/AiApprovalServer
```

启动后控制台会打印入口、数据目录、AI 状态与演示账号：

```
==============================================================
 AI Agent 安全执行与审批系统（星云游安全执行平台）
==============================================================
 用户前端   : http://127.0.0.1:8899/
 业务对接台 : http://127.0.0.1:8899/biz
 管理后台   : http://127.0.0.1:8899/admin
 数据目录   : <内容根>/App_Data
 AI 状态    : 未配置 → 本地意图解析 + 变更类操作全部转人工审批
 审批通知   : SMTP 未启用 → 通知写入出站箱（后台可查看/撤回）
```

| 页面 | 路径 | 用途 |
| --- | --- | --- |
| 业务工作台 | `/`（等同 `/index.html`） | 对话式下指令、查看审批状态与步骤、撤回申请 |
| 管理后台 | `/admin` | 审批、回退、用户管理、审计链校验、安全态势 |
| 业务对接台 | `/biz` | 甲方提交需求、乙方维护客户档案与需求单 |

- `/admin/`、`/admin/任意子路径` → 302 重定向到 `/admin`；`/biz/*` 同理。
- 其余未知路径统一返回 `404 {"ok":false,"code":"NOT_FOUND"}`，不区分"路径不存在"与"被安全策略忽略"。
- 健康检查（无需登录）：`GET /api/public/health`，返回 `aiConfigured` / `aiStatus` / `mode` / `selfRegistration` 等。

### 2.3 内容根与数据目录的落点

程序按顺序寻找"内含 `wwwroot` 的目录"作为内容根：可执行文件所在目录 → 当前工作目录 → 可执行文件上溯三级。

- `dotnet run` 场景：内容根是构建输出目录（`AiApprovalServer/bin/<配置>/net8.0/`），因此**默认数据目录就是该目录下的 `App_Data/`**，不是源码目录。
- 发布运行场景：内容根是发布目录，数据默认落在发布目录下的 `App_Data/`。
- 想固定位置：用 `AISERVER_DATA_ROOT` 指定绝对路径（推荐生产这么做）。

### 2.4 改监听地址

优先级：`AISERVER_LISTEN_URL` 环境变量 → `Server:ListenUrl`（`appsettings.json` 或 `Server__ListenUrl` 环境变量）→ 默认 `http://127.0.0.1:8899`。

```bash
# 换端口（Windows PowerShell）
$env:AISERVER_LISTEN_URL = "http://127.0.0.1:9000"
dotnet run

# 换端口（Linux/macOS）
export AISERVER_LISTEN_URL="http://127.0.0.1:9000"
dotnet run
```

说明：

- 只监听回环是**刻意的默认值**。改成 `http://0.0.0.0:8899` 会直接暴露明文 HTTP，请先读第九节。
- 启动横幅会把 `0.0.0.0` 与 `+` 显示成 `127.0.0.1` 以便点击，**实际监听地址仍以配置为准**。
- 服务端在 Kestrel 层额外施加了请求上限：请求体 `Security:MaxRequestBodyBytes`（默认 262144 字节）、请求头超时 15 秒、Keep-Alive 60 秒，并关闭 `Server` 响应头。

## 三、配置体系与优先级

配置有三个来源，**生效优先级从高到低**：

| 优先级 | 来源 | 形式 | 示例 |
| --- | --- | --- | --- |
| 1 | 专用环境变量 | `AISERVER_*` | `AISERVER_LISTEN_URL`、`AISERVER_AI_KEY` |
| 2 | .NET 标准环境变量覆盖 | `节点__字段`（**双下划线**） | `Ai__BaseUrl`、`Mail__Password`、`Limits__BanMinutes` |
| 3 | 配置文件 | `appsettings.json` | `"Ai": { "Model": "deepseek-chat" }` |
| 4 | 代码内置默认值 | `AppConfig.cs` | 见第四节每一行的"默认值"列 |

补充约定（均为代码实际行为）：

- `appsettings.json` 里所有以 `//` 开头的键（如 `"//ApiKey"`）只是**给读者看的注释替身**（JSON 不支持注释），程序不会读取它们。
- 空白字符环境变量等同于"未设置"（值为空白时按缺省处理）。
- **整数项如果配置成 0 或负数，会被当作"未配置"回退到内置默认值**（`Int()` 只接受 `> 0`）。想把某项调到 0 是做不到的，需要改代码或换用更小的正值以外的方案。
- 布尔项解析失败时回退默认值，不报错。

绝不要把真实密钥提交进仓库：`.gitignore` 已忽略 `App_Data/`、`secrets.json`、`appsettings.Local.json`、`appsettings.*.Local.json`、`.env`。**推荐把真实密钥写在环境变量或 `appsettings.Local.json`（不提交）里。**

## 五、密钥管理

### 5.1 三类密钥与用途

| 密钥 | 用途 | 派生方式 |
| --- | --- | --- |
| JWT 密钥（`jwt` / `AISERVER_JWT_SECRET`） | 登录令牌签名（HS256）与审批链接令牌签名 | 经HMAC-SHA256 派生出 `jwt`、`approval-link` 两把用途隔离的子密钥 |
| AES 主密钥（`aes` / `AISERVER_AES_KEY`，base64 32 字节） | 加密用户原始指令（`tasks.json` 的 `rawInputCipher`）与账号邮箱 | 经 HMAC-SHA256 + pepper 派生出 `raw-input`、`email` 两把子密钥 |
| SecretPepper（`AISERVER_PEPPER`） | 参与上面 AES 子密钥派生（用途隔离的额外一层） | 直接拼接进派生输入 |
| AI API Key（`AISERVER_AI_KEY`） | 访问模型接口，只出现在请求头，不落日志/审计/响应 | 不派生 |

### 5.2 `App_Data/secrets.json` 自动生成

首次启动、且 JWT/AES 密钥既没有环境变量也没有配置项时，程序会**随机生成**密钥并写入 `<数据目录>/secrets.json`（非 Windows 上会把文件权限收紧为仅属主可读写），控制台打印提示：

```
[提示] 已自动生成服务端密钥并写入 App_Data/secrets.json；生产环境请改用环境变量注入。
```

读取优先级：环境变量 → `appsettings.json` → 已存在的 `secrets.json` → 生成新的。

两个必须知道的细节：

1. **一旦你用环境变量提供了 JWT 密钥，`secrets.json` 不会被更新**（只有"密钥来自生成/persisted"时才会回写）。文件里可能残留旧值，属于无害残留，但排查时别被它误导。
2. **删掉 `secrets.json` 且不提供环境变量 = 换了一套新密钥**：旧登录令牌全部失效、`rawInputCipher` 与邮箱密文将无法解密。备份时必须带上这个文件。

### 5.3 `Security:StrictSecrets` 的真实含义

`Security:StrictSecrets=true` 时，如果 **JWT 密钥** 在"环境变量 / `Security:JwtSecret` / 已存在的 `secrets.json`"三处都缺失，程序抛异常并**拒绝启动**：

```
Security_StrictSecrets=true 但未提供 JWT 密钥（环境变量 AISERVER_JWT_SECRET 或 Security:JwtSecret）
```

需要如实了解的边界：

- **只检查 JWT 密钥**。AES 密钥不参与该检查；AES 密钥非法（不是 32 字节 base64）时只会记一条警告并重新生成。
- **自动生成的 `secrets.json` 也满足该检查**。也就是说，如果数据目录里已经有这个文件，开 `StrictSecrets=true` 并不能证明"密钥确实来自环境变量"。
- 想要"密钥缺失就不许启动"的效果，正确做法是：**生产部署时不要保留自动生成的 `secrets.json`**，并同时满足 `StrictSecrets=true` + 注入 `AISERVER_JWT_SECRET`。

### 5.4 密钥轮换与影响

**轮换 JWT 密钥（`AISERVER_JWT_SECRET`）**

1. 生成新密钥（例如 `openssl rand -base64 48`），通过环境变量/密钥管理服务注入。
2. 重启服务。
3. 影响：**所有已签发的登录令牌立即失效**，所有人需要重新登录；**所有尚在有效期内的邮件审批链接令牌同时失效**（审批令牌用 JWT 密钥派生的 `approval-link` 子密钥签名），此时待审批任务只能由管理员登录后台点击"同意"处理。
4. `secrets.json` 里若存有旧值不会被改写，可自行清理。

**轮换 AES 密钥（`AISERVER_AES_KEY`）或 pepper（`AISERVER_PEPPER`）**

1. 用 `openssl rand -base64 32` 生成新密钥（必须是 32 字节），注入后重启。
2. 影响：**历史密文不可解密** —— `tasks.json` 里的 `rawInputCipher`（用户原始指令）在审批页显示为空，账号邮箱密文同样读不出。**任务状态、文件、数据集、审计链不受影响**，服务可正常继续工作。
3. 涉及法务/审计留痕要求时，轮换前请先导出待审批任务上下文。

**只想让"某个人"下线，不要轮换全局密钥**

用户改口令、改角色、被禁用/启用时，程序会把该账号的 **令牌纪元 `epo`（`UserRecord.TokenEpoch`）加一**；
令牌校验时会比对 `payload.epo` 与账号当前值，不一致即视为无效。因此这四种操作**立即失效该用户的全部旧令牌**，且不影响其他用户、也不需要动全局密钥。

**轮换 AI API Key**

在模型服务商后台作废旧 Key → 注入新 Key → 重启（或重新部署）。本服务不缓存 Key，重启即生效。

## 六、数据目录

### 6.1 目录结构

默认位置：`<内容根>/App_Data`（可用 `AISERVER_DATA_ROOT` 改为绝对路径）。首次启动自动创建，典型结构如下：

```
App_Data/
├── users.json            账号表（含口令 PBKDF2 摘要、角色、TokenEpoch、锁定状态、AI 配额计数、邮箱密文）
├── users.json.bak        上一个版本的自动备份
├── tasks.json            审批任务全生命周期（含加密的原始指令 rawInputCipher、规则结论、AI 审核意见、注入特征）
├── versions.json         版本/快照记录（文件与数据集的变更前内容、撤销日志）
├── outbox.json           出站通知（审批链接、状态 QUEUED/SENT/FAILED/RECALLED）
├── audit.jsonl           审计日志，JSONL 逐行追加 + 哈希链（只追加，不重写）
├── secrets.json          首次启动自动生成的 JWT/AES 密钥（生产应改为环境变量注入）
├── datasets/
│   ├── customers.json    客户档案
│   ├── requirements.json 需求单
│   ├── orders.json       订单
│   └── contracts.json    合同
├── workspaces/
│   ├── u_<userId>/       每个账号的私人工作区（按账号 ID 命名）
│   └── share/            员工共享区（首次启动写入示例文件"运营协作须知.md"）
├── blobs/                版本库内容寻址存储（versions.json 指向的具体内容）
└── *.tmp  *.bak          原子写中间文件与上一版备份（维护任务会清理超过 30 分钟的 .tmp）
```

要点：

- `datasets/<名称>.json` 为**数据集**文件，内置 `customers` / `requirements` / `orders` / `contracts` 四张表。
- **通知的"出站箱"是 `outbox.json` 这个文件，不存在 `outbox/` 目录**，运行期不会创建它。
- 每个 JSON 文件采用"临时文件写入 + 覆盖式替换"的原子写，替换前把旧文件复制为 `.bak`：**不会出现半截 JSON**，`.bak` 可用于人工回滚。
- 读取时若 JSON 损坏会**抛错而不是返回空集合**，避免"看起来数据被清空"再被写回。
- `audit.jsonl` 只追加；多实例并发写同一文件时会加独占锁并在写前重读文件尾部校准链头。

### 6.2 备份与恢复

| 事项 | 建议做法 |
| --- | --- |
| 备份对象 | **整个数据目录**（含 `secrets.json`、`audit.jsonl`、`blobs/`） |
| 一致性 | 优先"停服后复制"或用文件系统/云盘快照。运行中直接复制可能抓到 `.tmp`，恢复时应丢弃 |
| 恢复 | 停服 → 用备份整体覆盖数据目录 → 启动；随后在管理后台执行"审计链校验"确认链未断 |
| 权限 | 目录只对服务运行账号可读写（含 `secrets.json`、`audit.jsonl`） |
| 保留 | `audit.jsonl` 建议按合规要求长期保留，并可另行归档（它是哈希链，改动会断链） |
| 迁移 | 换机器时数据目录与 `secrets.json` 必须一起搬，否则密文读不出、登录态全失效 |

### 6.3 迁移数据目录

```bash
# Windows PowerShell（绝对路径）
$env:AISERVER_DATA_ROOT = "D:\aiapproval-data"

# Linux/macOS
export AISERVER_DATA_ROOT="/var/lib/aiapproval"
```

- 只改路径**不会**自动搬数据，需要人工复制旧目录内容到新目录。
- 相对路径按"内容根"解析；`dotnet run` 时内容根是构建输出目录（见 2.3）。
- 该目录必须对服务运行账号**可写**（会创建子目录与追加审计行）。

## 七、AI 接入

### 7.1 基础配置

```bash
# Windows PowerShell
$env:AISERVER_AI_KEY = "sk-<your-key>"
$env:Ai__BaseUrl = "https://api.deepseek.com/chat/completions"
$env:Ai__Model = "deepseek-chat"
dotnet run
```

```bash
# Linux/macOS
export AISERVER_AI_KEY="sk-<your-key>"
export Ai__BaseUrl="https://api.deepseek.com/chat/completions"
export Ai__Model="deepseek-chat"
dotnet run
```

**"已配置"的判定条件比想象中严格**：API Key 必须**以 `sk-` 开头且长度大于 20**，否则系统认为 AI 未配置，直接进入降级模式（`/api/public/health` 的 `aiConfigured` 会是 `false`）。用自建网关的短 token（例如 `local-dev-token`）时会命中这个条件，请改用形如 `sk-<至少 21 个字符>` 的占位 Key。

### 7.2 出网白名单与协议校验

每次调用前都会校验 `Ai:BaseUrl`，两条硬规则：

| 检查 | 规则 | 失败原因文本（会出现在健康检查/日志里） |
| --- | --- | --- |
| 主机白名单 | `Uri.Host` 必须在 `Ai:AllowedHosts` 中（配置为空时等价于只放行内置的 `api.deepseek.com`） | `AI 接口主机不在白名单：<host>（自建网关请在 Ai:AllowedHosts 中显式放行）` |
| 协议 | 必须 `https`；**明文 `http` 仅在主机已被显式白名单放行、且该主机是本机/私网时**才允许 | `AI 接口必须使用 https（仅本机/内网自建网关可用明文 http）` |

被判定为"本机/私网"的地址包括：`127.0.0.0/8`、`10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`0/8`、`100.64/10`（运营商级 NAT）、`224/4` 及以上的多播/保留段；IPv6 含回环、链路本地、站点本地、ULA(`fc00::/7`)、多播。

**公网地址永远不能用明文 http**，这是防 SSRF 与防中间人的硬约束，不能通过配置绕过（只能改代码）。

调用行为：全程 `async/await` + 超时 + 重试（对 4xx 中的非 429 直接放弃重试）；全局并发受 `Ai:MaxConcurrentCalls` 限制；上游错误响应体**不会**被透传给调用方（只保留状态码），避免泄露密钥或内部信息。

### 7.3 自建 / 私有模型网关

```bash
# 例：公司内的 vLLM / 兼容网关（私网明文 http，需显式白名单）
$env:AISERVER_AI_KEY = "sk-<your-gateway-key-at-least-21-chars>"
$env:Ai__BaseUrl = "http://10.0.0.5:8000/v1/chat/completions"
$env:AISERVER_AI_ALLOWED_HOSTS = "10.0.0.5"
$env:Ai__Model = "your-model-name"

# 例：本机 Ollama 兼容端点
$env:Ai__BaseUrl = "http://127.0.0.1:11434/v1/chat/completions"
$env:AISERVER_AI_ALLOWED_HOSTS = "127.0.0.1"
```

注意事项：

- 请求体固定包含 `response_format: {"type":"json_object"}`（本服务要求模型输出 JSON）。**网关必须支持该字段**，否则会返回 4xx 并被判定为调用失败 → 降级。
- 多主机可逗号分隔：`AISERVER_AI_ALLOWED_HOSTS="api.deepseek.com,10.0.0.5"`。
- 白名单只校验 `Uri.Host`（不含端口），因此同一主机不同端口无需重复列出。

### 7.4 多步代理循环与配额

| 机制 | 说明 |
| --- | --- |
| 多步循环 | 只读工具（检索、读取、统计等）可像代码助手那样连续调用；**一旦出现写操作立即终止循环转人工审批**，不会边审批边继续跑 |
| 步数上限 | `Ai:MaxAgentSteps`（默认 5），每一步都是一次模型调用，达到上限用已有信息给结论 |
| 墙钟上限 | `Ai:AgentTimeoutSeconds`（默认 60 秒） |
| 每用户每日配额 | `Ai:DailyCallsPerUser`（默认 200），按 UTC 日期计数、跨日自动清零；用尽时当天回退本地意图解析，界面提示"今日 AI 调用额度已用尽（已用/上限）" |
| 全局并发 | `Ai:MaxConcurrentCalls`（默认 4） |
| 单用户对话限流 | `Limits:AgentChatPerFiveMinutesPerUser`（默认 20 / 5 分钟） |

成本控制建议：多人共用一个 API Key 时，先把 `DailyCallsPerUser` 调小（例如 50），再按实际用量放开。

### 7.5 未配置 / 不可用时的降级行为

这是本项目最重要的运维特性之一：**AI 不可用不会让防线变松，只会让智能变弱。**

| 状态 | 触发条件 | 行为 |
| --- | --- | --- |
| `off` | 没有 `Ai:ApiKey`，或 Key 不满足 `sk-` + 长度 > 20 | 本地意图解析生成单步计划；审核不可用 → **所有有副作用的操作强制转人工审批** |
| `degraded` | 已配置但最近一次调用失败（超时、网络、鉴权、结构解析失败等） | 同上；健康检查里能看到 `aiLastError`（只含异常类型与简短描述，不含密钥） |
| `online` | 最近一次调用成功（或配置后尚未调用过） | 正常多步代理 + AI 安全审核 |

判定依据是"最近一次成功/失败时间"的比较，因此**配置了 Key 不等于"AI 在线"**——界面与健康检查都区分这两种状态，不会给出误导性的"AI 在线"。

`/api/public/health` 返回的 `mode` 文本（实测原样）：

- off：`本地意图解析（AI 未配置）+ 审核不可用 → 变更类操作全部转人工审批`
- degraded：`AI 已配置但调用失败 → 已降级为本地意图解析，变更类操作全部转人工审批`
- online：`AI 意图解析 + AI 安全审核（物理隔离）`

`Ai:RequireApprovalWhenReviewUnavailable` 控制的是"审核不可用时是否强制人工审批"（默认 `true`）。关掉它只会放宽"审核不可用"这一种情形的兜底，**不会**放宽规则引擎的硬拦截（路径守卫、权限、共享区写、可执行文件识别等始终生效）。

## 八、邮件通知

### 8.1 行为模型（双通道）

1. **永远先落库**：通知先写进 `App_Data/outbox.json`（状态 `QUEUED`），因此后台始终能查看、补发、撤回（撤回 = 补偿事务，状态改为 `RECALLED`）。
2. **满足条件才真正发信**：`Mail:Enabled=true` **且** `Mail:Host` 非空 **且** 收件人非空。发送成功 → 标记 `SENT` 并写审计 `notify.sent`（收件人脱敏）。
3. **发信失败不影响主流程**：异常被捕获，通知标记 `FAILED`（错误信息截断 400 字符）并打警告日志，业务请求照常返回。
4. **未启用 SMTP 时**：只写审计 `notify.queued`，不阻塞任何流程。

### 8.2 审批链接与 `Mail:PublicBaseUrl`

审批链接的生成公式是：

```
{Mail:PublicBaseUrl}/admin?task={taskId}&token={签名令牌}
```

- `Mail:PublicBaseUrl` 未配置时取 `ListenUrl`（默认 `http://127.0.0.1:8899`），并去掉结尾 `/`。
- **它必须是"审批人浏览器能访问到"的地址**。若保持默认回环地址却把系统部署在服务器上，邮件里的链接点开是审批人自己的机器，等于失效。对外部署请设置为形如 `https://approval.example.com`。
- 令牌与任务绑定、有有效期（`Security:ApprovalTokenMinutes`，默认 240 分钟）、**一次性**；库里只存令牌摘要。改 taskId 或过期时间都会验签失败。
- 邮件正文**不含**用户原始指令与完整参数，只含任务编号、提交人、意图摘要、工具、风险等级、规则结论、审核意见与规范化动作，正文里明确提示"请登录后台查看完整上下文"。这是刻意的数据边界设计：不把敏感数据推出信任边界。

### 8.3 SMTP 配置样例

`appsettings.Local.json`（不提交）或环境变量：

```json
{
  "Mail": {
    "Enabled": true,
    "Host": "smtp.example.com",
    "Port": 587,
    "UseSsl": true,
    "Sender": "approval@example.com",
    "Password": "<smtp-password>",
    "ApproverAddress": "security-approver@example.com",
    "PublicBaseUrl": "https://approval.example.com"
  }
}
```

等价的局部环境变量：

```bash
export Mail__Enabled=true
export Mail__Host=smtp.example.com
export Mail__Port=587
export Mail__UseSsl=true
export Mail__Sender=approval@example.com
export AISERVER_MAIL_PASSWORD="<smtp-password>"
export Mail__ApproverAddress=security-approver@example.com
export Mail__PublicBaseUrl=https://approval.example.com
```

配置要点与坑：

| 事项 | 说明 |
| --- | --- |
| 发件人必填 | 发信使用 `MailMessage(Sender, to, ...)`，`Sender` 为空会发送失败并被记为 `FAILED` |
| 凭据注入条件 | 只有 `Sender` 与 `Password` **同时非空**才设置 SMTP 凭据；用匿名中继时才留空口令 |
| 加密方式 | `UseSsl=true` 走 STARTTLS（`SmtpClient.EnableSsl`）。**隐式 TLS 的 465 端口不受支持**；服务商只提供 465 时，建议在前面放一个支持 STARTTLS 的中继（如本机 postfix/msmtp），或改用 587/25 |
| 收件人 | `Mail:ApproverAddress` 是唯一的审批通知收件人，务必替换为真实审批人地址（仓库里的值是占位符） |
| 出站箱兜底 | 即使完全没配 SMTP，审批流仍然可用：管理员登录 `/admin` 即可看到待审批列表并处理，`outbox.json` 保留全部通知痕迹 |

## 九、反向代理与 TLS

### 9.1 默认姿态

默认 `http://127.0.0.1:8899` **只监听回环**，这是刻意的：服务本身不做 TLS，直接暴露到公网等于把口令与令牌明文传输。

对外提供的推荐架构：

```
浏览器 ──https──► 反向代理（同机，终止 TLS） ──http 127.0.0.1:8899──► 本服务
```

即：**保持本服务只监听回环**，让同机的 Nginx/Caddy 通过回环地址转发；不要改成 `0.0.0.0` 绕过代理。

对外部署时**必须处理来源校验**（TLS 在代理终止会让写请求被 403 拦下，见 9.2）：首选在 `Security:TrustedOrigins` 里填浏览器实际访问的来源，代理按常规透传 `Host` 即可；不想维护清单时再退到"代理改写 `Origin`"的备选做法。

### 9.2 写请求的来源校验：首选与备选

服务端对 `POST/PUT/PATCH/DELETE` 做来源校验，判定顺序是：

1. `Origin` 命中 `Security:TrustedOrigins` 白名单 → 放行；
2. `Origin` 与本服务看到的 `{Request.Scheme}://{Request.Host}` 严格同源 → 放行；
3. 其余 → `403 BAD_ORIGIN`。

**问题出在第 2 条**：当 TLS 在代理终止时，本服务看到的是 **http**，期望值变成 `http://<Host>`，而浏览器发来的是 `https://<Host>`，两者不等。以下为空白名单（默认值）时的实测结果：

| 实测场景（本机回环进程） | 结果 |
| --- | --- |
| `Host: 127.0.0.1:8899` + `Origin: http://127.0.0.1:8899` | 通过（登录 200） |
| `Host: example.com` + `Origin: https://example.com`（模拟代理终止 TLS，未配置白名单、未改写 Origin） | **403 `BAD_ORIGIN`** |
| `Host: example.com` + `Origin: http://example.com`（代理改写 Origin） | 通过 |
| `Host: example.com:8443` + `Origin: http://example.com:8443`（带端口，写法一致） | 通过 |
| 不带 `Origin` 头（curl/脚本客户端） | 通过（改由请求签名机制负责） |

#### 首选做法：配置 `Security:TrustedOrigins`，代理按常规透传 `Host`

把"浏览器实际访问的来源"填进白名单，代理不需要做任何 Origin 改写：

```bash
# 环境变量：多个来源用分号 / 逗号 / 空格分隔
export AISERVER_TRUSTED_ORIGINS="https://ops.example.com"
```

```json
{
  "Security": {
    "TrustedOrigins": [ "https://ops.example.com", "https://ops.example.com:8443" ]
  }
}
```

实测（每一种都是真实进程 + 真实请求）：

| 场景 | 结果 |
| --- | --- |
| 白名单为空 + `Origin: https://example.com` | **403**（与升级前行为完全一致） |
| 白名单 `https://example.com` + 同源不成立但命中白名单 | 通过（200） |
| 分号 / 空格分隔的多个来源，命中第二个 | 通过 |
| 逗号分隔的多个来源，命中第一个 | 通过 |
| 白名单写 `https://example.com:443` + `Origin: https://example.com`（默认端口被归一化） | 通过 |
| 白名单写大写 `HTTPS://OPS.EXAMPLE.COM` + `Origin: https://ops.example.com` | 通过（不区分大小写） |
| 白名单写 `example.com`（缺协议，非法） | 忽略该条目 + 启动打印 `[提示]` 警告，请求 **403** |
| 白名单 `https://other.example.com` + `Origin: https://example.com` | **403**（未命中不放行） |

填写要点：

- 必须是**带协议的完整来源**（`scheme://host[:port]`），**不支持通配符**：多个子域要逐个列出（如 `https://a.example.com,https://b.example.com`）。
- 只填"你自己对外提供服务的来源"，不要把无关站点写进来——写进来的来源其浏览器发起的写请求会被直接放行（其余防线仍然生效：Bearer 令牌、请求签名、限流、审计一个都不少）。
- 该白名单**只作用于写请求（`POST/PUT/PATCH/DELETE`）的来源校验**，且只影响这一处判定；**不改变**客户端 IP 判定、HSTS 判定等其他行为（读请求、以及不带 `Origin` 的脚本客户端本来就不受这条校验约束）。

#### 备选做法：保持空数组，由代理改写 `Origin`

如果不想在应用侧维护来源清单（例如域名经常变、代理层已有统一范式），可以保持 `TrustedOrigins` 为空，让代理把 `Origin` 归一化成"本服务看到的 scheme + 同一个 Host"：

```nginx
proxy_set_header Host   $http_host;
proxy_set_header Origin "http://$http_host";
```

要点：`Host` 必须原样透传，`Origin` 的 host 部分必须与它**逐字一致（含端口）**；实测这种改写可以让原本 403 的 `https://` 来源请求变为通过。

#### 为什么默认不启用 `ForwardedHeaders`（有意为之的取舍）

另一条看似"更正统"的路是启用 ASP.NET Core 的 ForwardedHeaders 中间件，让 `X-Forwarded-Proto` 把 scheme 修正成 `https`。本服务**刻意没有这么做**：

- ForwardedHeaders 只有在配置了 `KnownProxies` / `KnownNetworks` 时才是安全的。若不加限制地信任，任何能直连本服务的人都可以伪造 `X-Forwarded-Proto` / `X-Forwarded-Host`，等于把一个**可伪造的请求头**变成"scheme 与 host 的事实来源"。
- 而这个"事实来源"同时影响来源校验、HSTS 判定，以及审计与限流记录里的主机/IP 判定——一旦被污染，影响面比 403 大得多。
- 因此本服务选择：**只信任 TCP 对端地址**（客户端 IP 始终取连接对端）+ **来源校验用显式白名单**。代价是部署时多写一行配置，换来的是"默认配置下不存在可伪造的信任边界"。
- 若你确实要启用 ForwardedHeaders，必须同时正确配置 `KnownProxies`，且这属于代码改动（本仓库未做，不在支持范围内）。

### 9.3 其它两点：HSTS 与客户端 IP

`HSTS` 响应头只在 `Request.IsHttps` 为真时由本服务添加，代理终止 TLS 时不会出现，**需要在代理侧配置 HSTS**。

**客户端 IP：本服务只信任 TCP 对端地址**

`SecurityGuard.ClientIp` 直接取 `Connection.RemoteIpAddress`，**不解析 `X-Forwarded-For`**（避免可伪造头部污染封禁与审计）。带来两个后果：

- 反代之后，所有请求的 IP 都是代理机地址：`LoginPerFiveMinutesPerIp`、`AgentChatPerFiveMinutesPerIp`、`SelfRegistrationPerHourPerIp` 等**按 IP 的限流会退化成全局限流**。部署时按预期总流量适当放大这些阈值（账号级锁定 `LoginPerFifteenMinutesPerAccount` 仍按账号生效，是主要防线）。
- WAF 会扫描 `X-Forwarded-For` 头内容，因此**不要**把客户端自带的 XFF 链原样透传（既会被伪造，也可能触发 WAF），建议直接覆盖为直连对端地址。

### 9.4 Nginx 示例

以下为示例配置（**Nginx 本身未在真实环境验证**；其中 `Host` 透传与 `Origin` 改写两种做法都已在本服务进程上实测过）：

```nginx
# HTTP 强制跳转 HTTPS
server {
    listen 80;
    server_name ops.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    http2 on;
    server_name ops.example.com;

    ssl_certificate     /etc/letsencrypt/live/ops.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/ops.example.com/privkey.pem;

    # 本服务在非 https 请求上不会自己加 HSTS，请在代理侧加
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    # 与本服务 Security:MaxRequestBodyBytes 保持一致
    client_max_body_size 256k;

    location / {
        proxy_pass http://127.0.0.1:8899;
        proxy_http_version 1.1;

        # 首选：Host 原样透传即可，来源校验交给 Security:TrustedOrigins
        proxy_set_header Host              $http_host;
        # 备选（TrustedOrigins 保持为空时启用这一行，二选一，不要同时依赖）
        # proxy_set_header Origin          "http://$http_host";

        # 覆盖 XFF：本服务按 TCP 对端记录 IP，且 WAF 会扫描该头
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP         $remote_addr;

        # 多步代理循环最多 60 秒，留出余量
        proxy_read_timeout 120s;
        proxy_send_timeout 120s;
    }
}
```

配合首选做法时，服务端设置（与上面的 `server_name` 一致）：

```bash
export AISERVER_TRUSTED_ORIGINS="https://ops.example.com"
```

### 9.5 Caddy 示例

Caddy 自动申请并续期证书，写法更短（同样是示例配置，**Caddy 本身未验证**）：

```caddyfile
ops.example.com {
    encode gzip

    reverse_proxy 127.0.0.1:8899 {
        header_up Host {host}
        header_up X-Forwarded-For {remote_host}
        # 备选（TrustedOrigins 保持为空时启用这一行）
        # header_up Origin "http://{host}"
    }
}
```

> 首选做法下不需要 `Origin` 改写，只要把 `https://ops.example.com` 加进 `Security:TrustedOrigins`。
> 若走备选做法：`{host}` 的取值语义（是否含端口）请以你所用的 Caddy 版本为准，务必保证 `Host` 与 `Origin` 两处的值逐字一致。

### 9.6 必须透传 / 必须处理的请求头

| 请求头 | 处理方式 | 原因 |
| --- | --- | --- |
| `Host` | 原样透传（`$http_host`） | 来源校验与链接、审计里的主机信息以此为准 |
| `Origin` | **首选：不动它**，改用 `Security:TrustedOrigins` 放行浏览器来源；**备选：改写为 `http://<同一个 Host>`** | TLS 在代理终止时，未做处理会让写请求 403（9.2 实测） |
| `X-Forwarded-For` | 覆盖为直连对端地址 | 本服务不解析该头做 IP 判定，且 WAF 会扫描其内容 |
| `Authorization` | 原样透传 | Bearer 令牌认证 |
| `X-Timestamp` / `X-Nonce` / `X-Signature` | 原样透传，**不要改写** | 请求签名覆盖"方法 + 路径与查询串 + 时间戳 + nonce + 请求体哈希"，任何篡改都会验签失败；时间偏差需在 `Security:ClockSkewSeconds`（默认 300 秒）内，**代理机与服务机时间要同步（NTP）** |
| `Content-Type` / `Content-Length` | 原样透传，不要压缩/改写请求体 | 签名覆盖的是原始请求体字节 |

其他建议：静态资源由本服务自己提供即可（无需另配静态服务器）；如需在代理层加缓存，注意本服务对 `html/js/css` 已设置 `Cache-Control: no-store`，有意不缓存。

| 签名报"时间戳超出 N 秒有效期" | 客户端与服务器时钟偏差超过 `Security:ClockSkewSeconds`；校时（含代理机） |

| 邮件里的审批链接点开无效 | `Mail:PublicBaseUrl` 配成了回环地址，或令牌已过期/已被使用过（一次性），或 JWT 密钥刚做过轮换 |

| 审计链校验报"序号断裂/前序哈希不匹配" | `audit.jsonl` 被外部编辑或截断；从备份恢复，别尝试手工修补 |

| 端口被占用 | 改 `AISERVER_LISTEN_URL`，或结束占用 8899 的进程 |

## 十二、边界与未验证事项

为了让文档可核对，这里明确区分"代码可证"与"未验证"：

**已在本机真实进程上验证**

- 默认监听 `http://127.0.0.1:8899`；`AISERVER_LISTEN_URL` 可改监听地址（注意：`ASPNETCORE_URLS` **不生效**，本服务的监听地址由 `AISERVER_LISTEN_URL` / `Server:ListenUrl` 决定）
- `/`、`/index.html`、`/biz`、`/admin`、`/admin/` 返回页面，未知路径返回 404
- `Origin` 与 `Host` 的组合行为，空白名单下的严格同源判定（见 9.2 表格）
- `Security:TrustedOrigins` 的九种场景：命中和未命中、分号/逗号/空格三种分隔、非法条目（忽略 + 启动警告）、默认端口归一化、大小写不敏感、白名单为空时行为与升级前一致（见 9.2 表格）
- `/api/public/health` 的字段与 `mode` 文本
- AI 未配置时的降级链路（本地解析 + 变更类操作强制人工审批）

**按代码推导、但本文未做端到端实证**

- Nginx / Caddy 示例配置本身（这两个代理软件未实际运行；但示例所依赖的 `Host` 透传与 `Origin` 改写两种做法都已在本服务进程上实测）
- SMTP 实际投递（未接入真实邮件服务；行为描述来自 `Services/Outbox.cs`）
- `Security:TrustedOrigins` 通过 `appsettings.json` 数组下标（`Security__TrustedOrigins__0`）而非环境变量配置的路径（环境变量的分隔符形式已实测；数组形式与前者共用同一段解析代码）
- 直接用 Kestrel 承载 TLS：本服务不提供证书配置入口。理论上可用 `AISERVER_LISTEN_URL=https://0.0.0.0:8899` 配合 Kestrel 标准配置键（如 `Kestrel__Certificates__Default__Path` / `__Password`）实现（**未验证**）。推荐仍用反向代理终止 TLS
- Linux 下的服务化（systemd / 容器编排）未随仓库提供单元文件；注意用环境变量注入密钥，并把 `AISERVER_DATA_ROOT` 指向持久卷

**已知设计边界（有意为之，不是缺陷）**

- 单进程、JSON 文件存储，**没有数据库、没有分布式锁、没有水平扩展设计**；多实例同时写同一数据目录不在支持范围内（审计追加做了跨进程串行化，但其他文件没有跨机锁）
- 不解析 `X-Forwarded-*`，客户端 IP 以 TCP 对端为准（见 9.3）
- 不启用 ForwardedHeaders，来源校验改用显式白名单 `Security:TrustedOrigins`（理由见 9.2 末段）
- `Security:TrustedOrigins` 不支持通配符：子域必须逐个列出（见 9.2）
- `Security:StrictSecrets` 只覆盖 JWT 密钥（见 5.3）
- 整数配置项不接受 0 或负数（见第三节）
