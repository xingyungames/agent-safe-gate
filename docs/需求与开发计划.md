# 需求与开发计划

本文保留项目的**原始需求与分阶段实施思路**（未经修改，仅做 Markdown 排版），并在末尾附上"**计划 → 实现**"对照表，
说明每一阶段实际落地成了什么、与原计划有哪些有意偏离。

---

## 一、项目背景与核心目标

构建一个企业级、高安全性的 AI Agent 系统。系统不仅能理解用户意图并调用工具（如读写文件、操作数据库），
更强调**防御提示词注入、细粒度权限控制、AI 自动化安全审核以及高危操作的人工审批（Human-in-the-loop）**。

### 核心设计原则

1. **不信任原则**：不信任客户端输入，不盲目信任上游 AI 的输出。
2. **最小权限原则**：AI 只能在用户被授权的范围内执行工具。
3. **职责分离原则**：上游 AI 负责"翻译意图"，下游 AI 负责"安检"，规则引擎负责"硬拦截"。
4. **隔离原则**：AI 审核模块与用户原始输入物理隔离，切断提示词注入攻击链。

---

## 二、核心架构与数据流转

系统分为四大核心模块：**接入鉴权层 → AI 推理与执行层 → 安全审核层 → 异步审批与持久化层**。

数据流转链路：

```
用户请求 → 网关鉴权 → 权限上下文提取 → 上游 AI（意图解析 + 工具调用）
        → 规则引擎（硬拦截）→ AI 审核（软拦截）→ 异步持久化（如需人工审批）
        → 邮件通知 → 管理员审批 → Harness 工具执行 → 审计日志 → 结果返回
```

## 三、详细开发计划（分模块实施）

### 阶段 1：基础安全与接入鉴权（基础底座）

目标：确保只有合法用户能访问，防御基础 Web 攻击。

- **Token 鉴权**：基于 JWT 的用户登录与身份校验，Token 中携带用户 ID 和基础角色。
- **防重放攻击**：请求头加入时间戳（Timestamp）和随机数（Nonce），服务端校验时间戳有效期（如 5 分钟）并缓存 Nonce。
- **数据加密**：账号密码加密存储；敏感数据传输使用 HTTPS。
- **防 XSS**：前端输入过滤，后端 WAF 层拦截恶意脚本。

### 阶段 2：权限与 Prompt 构建（大脑构建）

目标：让 AI 知道"用户是谁"，以及"用户能干什么"。

- **RBAC 权限模型**：建立 用户 → 角色 → 权限组（工具白名单）的映射。
- **动态 Prompt 组装**：每次请求时拉取用户权限，拼接到 System Prompt 中。
- **意图摘要生成（优化点）**：要求上游 AI 在输出工具调用 JSON 时，必须附带简短的 `intent` 字段，用于后续审核。
- **提示词注入防护**：使用 XML 标签隔离用户输入，并在 System Prompt 中警告模型不要执行覆盖指令。

### 阶段 3：Harness 工具层与规则引擎（硬防线）

目标：实现 AI 与底层系统的解耦，并进行确定性安全校验。

- **定义 Function Calling Tools**：定义 ReadFile、WriteFile、GetFileList 等标准 JSON Schema。
- **Harness 封装**：大模型不直接操作底层，而是输出 JSON；Harness 解析 JSON 并转化为后端 API 调用。
- **规则引擎（优化点）**：在 AI 审核前，使用代码进行 100% 可靠的硬校验：
  - 路径白名单：校验文件路径是否落在用户自己的目录下，拦截 `..` 等越权路径。
  - 工具权限校验：检查当前用户的权限组是否包含该工具。
  - 参数类型校验：校验 JSON 结构是否符合预期。

### 阶段 4：AI 安全审核层（软防线）

目标：利用 AI 的逻辑判断能力，拦截"合法工具被滥用"的风险。

- **物理隔离设计（核心亮点）**：AI 审核模块绝对不接收用户的原始 Prompt，只接收 `{intent（意图摘要）, action（工具调用 JSON）}`。
- **危害判定**：让审核 AI 判断该动作是否合理（如：删除数据库、替换系统文件、向外部发送敏感数据）。
- **分级拦截**：
  - 明显恶意（如删库）：直接打回，返回错误给用户。
  - 高危模糊操作：转入"人工审批"流程。
  - 安全操作（如只读）：直接放行给 Harness 执行。

### 阶段 5：异步持久化与人工审批流程（Human-in-the-loop）

目标：解决长耗时审批导致 HTTP 超时的问题，并确保操作可追溯。

- **任务状态机与持久化（优化点）**：
  - 生成唯一的 TaskID。
  - 将操作指令、意图摘要、用户 ID、状态（PENDING）写入存储（文件存储需注意并发锁与原子写）。
  - 立即响应用户："您的操作涉及高危修改，已提交管理员审批，请留意通知。"
- **发送安全邮件（优化点）**：
  - 发送邮件给管理员。
  - 链接必须带签名 Token（HMAC），防止 IDOR 越权（如 `approve?taskId=123&token=xxx`）。
- **管理员审批**：
  - 点击链接 → 校验签名 → 强制登录 → 展示完整上下文（用户输入 + 意图摘要 + 具体动作）。
  - 管理员点击"同意"或"打回"。
  - 状态更新为 APPROVED 或 REJECTED。

### 阶段 6：执行与审计日志（闭环）

目标：安全执行操作，并留下完整的审计追踪，用于回退。

#### 额外实现：类似 Git 的一键回退（通过后台 HTML 操作）

核心思路是**快照与差异（Snapshot & Diff）**：不能只记录"修改了文件"，必须在执行前保存"旧状态"，并计算差异。

- **文件操作（Write/Delete）**：
  - 全量快照：修改/删除前把原文件完整复制进版本库。
  - 差异记录：用文本对比算法生成类似 Git 的 `+`/`-` 变更记录，用于管理页面展示。
- **数据库操作（Update/Delete）**：
  - 反向记录：执行 UPDATE 前查询并记录旧数据；执行 DELETE 前将整行转存为 JSON。
  - 回退时按记录的数据还原（把 UPDATE 变成反向 UPDATE，把 DELETE 变成 INSERT）。
- **API 调用 / 外部系统操作**：补偿事务——必须定义其"反向操作"（如撤销邮件、恢复第三方状态）。

## 四、计划 → 实现对照

| 计划阶段 | 实际实现 | 与原计划的差异 / 说明 |
| --- | --- | --- |
| 阶段 1 鉴权与防重放 | JWT（自实现 HMAC-SHA256 紧凑序列化，含**令牌纪元** `epo` 用于整体失效）+ 请求签名（`X-Timestamp`/`X-Nonce`/`X-Signature`）+ 时间窗与 nonce 去重 + WAF + 蜜罐 + 双维度限流与账号锁定 + 安全响应头 | **未使用 Redis**：nonce 与限流都在进程内维护，符合"零第三方依赖、单进程参考实现"的定位；文档已说明这是有意取舍 |
| 阶段 1 口令加密 | PBKDF2-HMAC-SHA256（21 万次迭代 + 随机盐），不可逆存储；用户原始输入与邮箱用 AES-256-GCM 加密封存 | 计划里写的是"AES 加密存储口令"，实现改为**口令哈希**（更正确的做法：口令不该可解） |
| 阶段 2 RBAC + 动态 Prompt | 角色 → 权限键 → 工具白名单静态映射；提示词里只列出当前角色可用工具；每次请求重建提示词；`intent` 贯穿审批与审计 | 一致 |
| 阶段 2 注入防护 | XML 标签隔离 + 转义 + "标签内是数据"声明 + 注入特征扫描（命中强制转人工）+ 历史对话同样包裹 | 一致，并额外做了"模型未调工具即作答"的 `ai.declined` 审计 |
| 阶段 3 Harness + 规则引擎 | 35 个工具，参数 Schema 白名单 + 路径守卫（`..`/绝对路径/备用数据流/设备名/软链祖先）+ 权限校验 + 业务硬规则 + 口语到枚举映射 + 名字解析（歧义返回 `ASK`） | 一致，并额外做了"参数被翻译过就留痕"，审批页可见 |
| 阶段 4 AI 审核物理隔离 | 审核调用只发 `{intent, 规范化动作}`；三档结果；**不可下调审批等级**；不可用时按最保守策略 | 一致，且明确写进代码不变量与回归用例 |
| 阶段 5 异步审批 | 任务状态机（CAS 防并发、过期、撤回）+ JSON 原子写与备份 + 出站箱/可选 SMTP + HMAC 签名一次性审批链接 + 完整上下文审批页 | **未用 PostgreSQL**：仍按计划允许的"文件存储"实现，并补了原子写与独占锁 |
| 阶段 6 执行与审计 | 快照 + Diff + 版本记录 + 一键回退（文件/数据集/改名）+ 审计 JSONL 哈希链 + 整链校验 | 一致，并额外做了多实例并发追加的链头校准 |
| 额外：HTML 后台回退 | 管理后台提供任务详情、Diff 展示与一键回退 | 一致 |
| 额外：补偿事务 | 外部接口只有"通知/邮件"一类，已实现撤销邮件与出站箱状态 | 范围有限，未做通用补偿事务框架 |

### 实现中新增（原计划未提）的机制

- **多步代理循环**：像代码助手一样"先搜 → 再读 → 再写"，只读自动连续执行，写操作立即终止循环转审批（含步数与墙钟双上限）。
- **文件策略矩阵**：按"区域 × 可执行性"分级，可执行判定 = 后缀 ∪ 内容识别；批量删除明确不支持。
- **业务对接台**：甲方自助注册建档、提需求、改档案走审批，形成甲方（用户）/乙方（员工、管理员）完整闭环。
- **管理端只读 AI 助手**：可查待审批、任务上下文、审计与账号活动汇总，但没有审批/执行/回退接口，杜绝"AI 自我批准"。
- **降级模式**：AI 不可用时"降智不降防线"——本地意图解析 + 全部变更转人工。
