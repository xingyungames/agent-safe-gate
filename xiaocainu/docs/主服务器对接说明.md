# 主服务器对接说明（前端 → 主服务器 → 飞书）

本文说明前端（小财奴网关）如何把**报销单写入口**交给主服务器 `AiApprovalServer`，
以及本地联调的两个进程怎么起、怎么验证。

---

## 一、为什么要接这一层

报销单的写入必须唯一，否则会出现三种不可接受的后果：

| 问题 | 直连飞书 | 走主服务器 |
| --- | --- | --- |
| 谁能写、写成什么值 | 前端自己判断，规则散落在业务代码里 | 服务端枚举白名单 + 金额区间 + 状态流转统一收口 |
| 申请人/工号是谁 | 前端传什么写什么 | 按登录令牌**服务端盖章**，前端伪造无效（实测覆盖成功） |
| 出错了能不能退 | 只能人工去表里改 | 每次写前存整行快照，管理员可按日志一键回退 |
| 事后能不能追 | 飞书表只剩结果 | 审计哈希链记录谁在什么时候改了什么 |

因此本仓库的做法是：**前端只负责"翻译与交互"，写库统一走主服务器**。

## 二、代码改动一览

新增文件：

| 文件 | 作用 |
| --- | --- |
| `api/backend_client.py` | 主服务器适配器（纯标准库）：登录换令牌、HMAC 请求签名、提交/查询/审核/契约元数据 |

改动文件：

| 文件 | 改动 |
| --- | --- |
| `api/auth_service.py` | 登录改为**先请主服务器判定口令**（同一套账号口令），成功后再用主服务器返回的账号资料签发本网关会话；令牌缓存供后续提交复用 |
| `models/agent.py` | 新增 `_submit_via_backend()`；`_do_submit()` 与 C 分支的合规回写改为"先走主服务器" |

| `models/users.py` | 修掉一个会导致网关**启动即崩**的导入 bug（见第六节） |
| `.env` / `.env.example` | 新增 `BACKEND_BASE_URL` / `BACKEND_TIMEOUT`（`BACKEND_MODE` 已随回落路径删除） |

## 三、配置

```ini
# 主服务器地址（必填）：登录判定、角色权限、报销单读写全部经此服务
BACKEND_BASE_URL=http://127.0.0.1:8899
# 单次 HTTP 超时（秒）；列表要拉 500 条，别设太小
BACKEND_TIMEOUT=20
```

失败语义只有一种：**不回退**。

| 失败类型 | 例子 | 行为 |
| --- | --- | --- |
| 业务拒绝 `BackendRejected` | 口令错误、无票阻断、部门不在枚举内、金额越界、事由缺失、限流 429 | 原样回给用户，**绝不绕过** |
| 令牌失效 `BackendUnauthorized` | 令牌过期、账号被改密/改角色/停用 | 401，让用户重新登录 |
| 基础设施故障 `BackendUnavailable` | 主服务器没起、超时、5xx、来源 IP 被安全策略封禁 | 503，提示稍后重试 |

> 早先的 `BACKEND_MODE=preferred`（连不上时回落直连飞书）已**删除**：
> 它会让一笔单绕过写入口、版本快照与审计，与"唯一写入口"直接冲突。

## 四、本地联调：两个进程

### 1) 主服务器（先起，因为前端登录时会先请它判定口令）

```powershell
cd <仓库>\AiApprovalServer
Copy-Item config\secrets.local.example.json config\secrets.local.json   # 填真实飞书凭证（已 gitignore）
dotnet run
```

启动日志里应看到：

```
 用户前端   : http://127.0.0.1:8899/
 财务工作台 : http://127.0.0.1:8899/finance
 账号权威   : users.json（本机 JSON）；飞书镜像 已启用（demo 口令模式，失败静默）
```

### 2) 前端网关

```powershell
cd <仓库>\xiaocainu
python -m venv .venv
$env:PYTHONUTF8 = '1'                      # requirements.txt 是 UTF-8，GBK 环境必须先开这个
.\.venv\Scripts\python.exe -m pip install fastapi uvicorn
.\.venv\Scripts\python.exe -m api.main 127.0.0.1 8000
```

浏览器打开 `http://127.0.0.1:8000/`（不要用 `0.0.0.0:8000`）。

> 前端同学机器上的 `run_server.bat` 里写死了他那台机器的 venv 路径，
> 换机器后要么改这个路径，要么直接用上面两条命令。

### 3) 验证三跳

| 跳 | 验证方式 | 期望 |
| --- | --- | --- |
| 前端 → 主服务器 | 前端登录一次，看返回体里的 `user` 与 `perms` | `角色=员工、工号=E0001`，`perms` 含 `invoice.submit`；网关侧已无本地账号表可兜底 |
| 主服务器 → 飞书 | 主服务器 `/finance` 页面看单据列表 | 能看到飞书主表真实数据 |
| 前端 → 主服务器 → 飞书 | 前端对话框里说完整一句单（部门/类型/金额/票据/事由），确认提交 | 答复里带 `BX-` 单号；飞书主表出现该行，且「申请人」「工号」是登录人本人 |

### 4) 离线单测（不起网关也能验）

```powershell
cd xiaocainu
python -m pytest tests/test_backend_authority.py -q   # 7 项：主服务器接受 / 拒绝 / 不可达 / 未启用 四种登录情形与角色映射
python -m pytest tests -q                             # 全套（171 项，纯离线）
```

## 五、字段与枚举口径

前端**不需要**传这些（传了也会被服务端覆盖）：`申请人`、`工号`、`记录提交时间`、`合规结果`、`风险摘要`、`状态`。
`单号`由飞书自动编号生成，主服务器写完会回取并返回 `bill_no`。

前端需要传的字段（枚举以 `GET /api/invoice/meta` 为准，不要手抄）：

| 字段 | 说明 |
| --- | --- |
| `department` | 部门（11 个枚举） |
| `rtype` | 报销类型（差旅费/招待费/办公用品/交通费） |
| `amount` | 金额，0.01 到 100000 |
| `reason` | 事由，2 到 200 字（**必填**：服务端会拒绝空事由） |
| `hasInvoice` | 票据状态（有票/无票/未提）；无票会被阻断 |
| `city` | 城市（差旅费必填，37 个枚举） |
| `invoiceDate` | 发票日期，适配器会把 `2026/10/3`、`2026年10月3日` 等归一为 `YYYY-MM-DD` |
| `invoiceInfo` | 发票号码；销售方（可选，OCR 结果） |

日期统一由适配器归一，前端继续用它原来的写法即可。

## 七、回退与排障

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 登录返回 503「主服务器暂时不可用」 | 主服务器没起 / 地址不对 | 起主服务器，核对 `BACKEND_BASE_URL`；网关已无本地账号表，不会再降级登录 |
| 登录直接报"用户名或口令错误" | 主服务器明确拒绝（口令错、账号停用、账号锁定、限流） | 这是最终结论，不会回落；按提示找主服务器管理员核对账号 |
| 登录报「主服务器暂时不可用，无法登录」 | 主服务器不可达 | 起主服务器后重试 |
| 提交后答复是"这张单没有提交成功：…部门必须…" | 业务规则拒绝（不回落） | 按提示改数据后重新确认提交 |
| 提交后答复「主服务器暂时不可用，单据没有提交」 | 主服务器不可达（fail-closed） | 起主服务器后重新确认提交；此时飞书里不会有半成品单据 |
| 同一笔单出现两行 | 旧版本 `preferred` 模式回落直连飞书写过一次 | 当前版本已无直连写单路径，不会再有；历史重复行以主服务器那条（有审计与版本）为准 |
| 想看某笔单能不能回退 | 主服务器写入口每次都存快照 | 管理后台「版本与回退」按日志回退；删掉的行会按快照重建（单号由飞书重新分配） |

## 八、账号权威边界（谁说了算）

**唯一权威：主服务器。** 网关不保存任何账号数据，也没有第二套口令校验。

| 事项 | 正确做法 | 为什么 |
| --- | --- | --- |
| 登录判定 | 网关调 `POST /api/auth/login`，由它决定放不放行 | 网关侧已无本地/飞书账号表可回落 |
| 新增账号 | 主服务器管理后台「账号管理」创建 | 工号由主服务器自增分配，网关不建号 |
| 改角色 / 停用 / 重置口令 | 主服务器管理后台操作 | 变更后旧令牌立即失效（`tokenEpoch`），网关收到 401 会让用户重登 |
| 角色与权限 | 网关只读主服务器下发的权限键（`invoice.*`） | 不再比较中文角色串，也没有"默认员工"这种隐式降级 |
| 会话令牌 | 浏览器持有主服务器 JWT，网关透传 | 网关不签发、不改写；登出只清网关缓存（主服务器无吊销列表） |
| 飞书用户表 | **已下线**；主服务器 `Feishu:UserTableId` 留空即整条镜像链路静默跳过 | 账号不再需要经第三方表格流转 |

> 完整设计与取舍见 `docs/账号统一改造-RFED_CAC.md`。

## 九、登录失败计数的口径（组合锁）

网关每次登录都会带 `X-Client-Ip: <真实客户端 IP>`。

主服务器只在「来源地址 ∈ `Security:TrustedProxies`」时才采信这个头，否则一律按 TCP 对端地址计
（防伪造：攻击者直连主服务器自己填这个头是无效的）。

失败计数键 = `用户名|IP`：

| 场景 | 结果 |
| --- | --- |
| 同一 IP 对同一账号 15 分钟内失败 5 次 | 只限制**该 IP 对该账号**的登录 15 分钟 |
| 换一个 IP 登录同一账号 | **正常放行**（密码正确即成功） |
| 登录成功 | 立即清空该组合的失败记录 |
| 账号不存在 | 不计数（避免被随机用户名刷爆内存） |

这样攻击者连错密码只能锁住自己，**锁不到别人的账号（包括管理员）**。

网关侧另有独立限流（`用户名|IP`，5 次/300 秒，仅失败计数），两层互不依赖，主服务器不可用时网关仍能自保。
